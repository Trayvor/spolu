# Permissions

Product rules are in [roles-and-access](../product/roles-and-access.md). In the product there are two roles, administrator and client; the superadmin is an administrator who cannot be deleted or demoted. In the database `User.role` is `superadmin | admin | client`.

| capability                                     | superadmin | admin                                       | client                                     |
| ---------------------------------------------- | ---------- | ------------------------------------------- | ------------------------------------------ |
| See all groups                                 | yes        | yes                                         | no, only their own groups                  |
| Create groups, copy invite links               | yes        | yes                                         | no                                         |
| Read and write chat, tasks, tickets in a group | all groups | all groups                                  | own groups only                            |
| Contracts module                               | yes        | yes                                         | no (not shown at all)                      |
| Global tickets list ("Technical support")      | yes        | yes                                         | no                                         |
| Bulk email ("Hromadné e-maily")                | yes        | yes                                         | no (not shown at all)                      |
| Create other admins                            | yes        | yes                                         | no                                         |
| Remove an admin                                | yes        | yes                                         | no                                         |
| Be removed or demoted                          | never      | yes, by another admin (never by themselves) | yes (assumed, confirm in the phase design) |
| Remove a client from a group                   | yes        | yes                                         | no (confirmed in Phase 3)                  |
| Message users of other organizations           | n/a        | n/a                                         | no                                         |

## The rule

Permissions are enforced on the server, in one place per module. Each module exports policy functions such as `canReadGroup(user, groupId)`. The same functions are used by HTTP routes and by socket room joins, so there is one definition of "who may see what".

Client-side hiding of buttons and pages is cosmetic. The server never trusts the client.

Bulk email policy lives in `modules/bulk-email/policy.ts`: `canUseBulkEmail(actor)` is `isAdmin(actor)` (Phase 23, owner decision 3: every admin edits, sends, cancels and deletes any campaign; no per-campaign owner). Its routes use `requireAdmin`, except the public image route, which checks a random image id, the four public unsubscribe routes (`GET`/`POST /api/bulk-email/unsubscribe/:token`, `POST …/unsubscribe/:token/one-click`, `POST /api/bulk-email/subscribe/:token`; `modules/bulk-email/unsubscribe-routes.ts`), which check the signed token (`modules/bulk-email/token.ts`, constant-time HMAC) and act only on the token's person, answer `404` for a bad signature or a deleted person, tell only `{ language, subscribed, test }`, allow 30 calls a minute per IP and are exempt from the CSRF guard, and `GET`/`PUT /api/me/bulk-email`, which need a session (`requireUser`, any role) and act only on the signed-in person (parts 23.2–23.4). Login codes, invites, notifications and ticket emails never read the bulk email setting (P5). Part 23.2 built the campaign and audience routes (`modules/bulk-email/routes.ts`): each runs `requireAdmin`, then `canUseBulkEmail`. Part 23.5: `POST …/campaigns/:id/test`, `…/send`, `…/cancel`, `GET …/campaigns/:id/recipients` and (part 23.7) `GET /api/bulk-email/sender` (the From address, for the send dialog) are in the same plugin (`requireAdmin`, then `canUseBulkEmail`); a test send goes only to the signed-in admin's own address, never to an address from the request. Part 23.3: `POST /api/bulk-email/images` and `POST /api/bulk-email/campaigns/:id/preview` are `requireAdmin` (client 403, anonymous 401); `GET /api/bulk-email/images/:id` is public and reads only a `bulk_images` row by its UUID, never a storage key from the request, so nothing else in storage is reachable through it.

User policy lives in `modules/users/policy.ts`: `isAdmin`, `canManageAdmins` (any admin) and `canDeactivate` (target is an admin, not the actor; the superadmin is never a target).

Group policy lives in `modules/groups/policy.ts`: `canManageGroups` (any admin), `canReadGroup(actor, groupId, actorGroupIds)` (any admin, or a client with an active `client` membership of `groupId`; `actorGroupIds` comes from `clientGroupIds` in `modules/groups/memberships.ts`, so a client of several groups reads each of them and a `ziadatel` membership never opens a group) and `canRemoveMember` (admin actor, client target). Removing a client from a group (`DELETE /api/groups/:id/members/:userId`) marks only that membership removed (`removed_at`); the account is disabled, its sessions revoked and its sockets closed only when no active membership is left. Restore clears `removed_at` and re-enables the account; only a restored `client` membership puts the person's sockets back into the group room. The same remove and restore routes act on requesters (`ziadatel` memberships): `GET /api/groups/:id/requesters` follows `canReadGroup` (admins and the group's clients; requesters are listed whether or not they have signed in yet) and `GET /api/groups/:id/requesters/removed` is admins only (`canManageGroups`). An invite never restores a removed membership. Group managers are set two ways. `canBeManager` (any admin) guards `PUT` and `DELETE /api/groups/:id/managers/me`, which act on `request.user` and answer `{ managers, managedByMe, mode }` with the caller's effective notification mode for the group. `canSetManager` (any admin) guards `PUT` and `DELETE /api/groups/:id/managers/:userId` (the group's Members tab), which make any active admin a manager or stop them being one and answer `{ managers }`; a target that is a client, disabled or unknown answers `403 forbidden` (`NotAnAdminError`). The `/me` routes are registered first, so `me` is never read as an id. A client gets `403 forbidden` on all four (no session: 401). An unknown group answers `404 not_found`; the calls are idempotent and share one rate limit per acting admin (120 a minute, `429 rate_limited`). The target's notification mode changes the same way whoever acts (`startManagerMode` / `stopManagerMode`). `GET /api/groups` (admins) lists each group's active `managers` and `managedByMe` for the caller. A group a caller may not read answers `404 not_found`, never 403, so group ids cannot be probed. `GET /api/groups/:id/people` follows `canReadGroup`; who counts as a person of the group is decided in `modules/groups/service.ts`, not by a policy function. There are two sets. The **readers** (`listGroupPeople`) are the named, verified, active clients of the group (an active `client` membership; requesters are not readers) and all active admins; each item carries `isManager` (true only for an admin with a `group_managers` row for this group, one query with a left join). Readers are who can be mentioned, shown as authors and notified. The **pickable people** (`listPickablePeople`, `isPickable` in `packages/shared`) are the group's clients and its active managers, not every admin: they are who can be picked as an assignee. Chat mentions and @all use the pickable people (`listPickablePeople`): the group's clients and its active managers. A task's new assignees are checked in one query with `getGroupPeopleRoles` and `canAssignTaskTo` (`modules/tasks/policy.ts`). Knowledge excerpts, search text and the calendar body show a mentioned name only for a member of the item's group or an admin; anyone else renders as `@?`. Adding members by email (Phase 22b) is admins only (`canManageGroups`; clients get `403 forbidden` on all three routes, because the answers reveal whether an account exists): `POST /api/groups/:id/members` (`{ email, name? }`; 201 `invited` or `added`, 200 `resent`; 409 `already_member`, `removed` with `userId`, or `email_taken_admin`; 400 `validation_failed`; 30 a minute per acting admin, `429 rate_limited`), `GET /api/groups/:id/members/invited` and `DELETE /api/groups/:id/members/invited/:userId` (204; 404 unless it is an active `client` membership of a user with `email_verified = false`, so it never touches a signed-in or removed member: removal stays `DELETE /members/:userId`). An admin's invite is a client membership created at once (`inviteMember`), not a `pending_invites` row: the admin is trusted, and a pending invite could be overwritten by any link the person opens later. A signed-in client added this way joins the group's room at once. File policy lives in `modules/files/policy.ts` (plus registered read rules, Phase 21: `files/read-rules.ts`; a file attached to a live message of a ticket chat the actor reads, or uploaded with a ticket the actor reads (`ticket_attachments`, `fileOfReadableTicket`), is readable, never an admins-only file): `canReadFile(actor, file, actorGroupIds)` follows the file's group (`canReadGroup`; an unreadable file answers `404 not_found`), except that a file with `admins_only` set (a file of an admins-only knowledge item, Phase 17) is readable by admins only, so the group's clients get `404 not_found` for it; a file of no group (sent to the ticket intake for a ticket without a client) is readable by admins only until the ticket gets its client and the file moves there; `canSetPreview` allows the uploader only (a file received from the intake has no uploader, so nobody sets its preview). Files API: anyone who reads the group may upload to it (`POST /api/groups/:id/files`); anyone who reads a ticket with a client may upload to that client's files through `POST /api/tickets/:id/files` (Phase 21, part 21.4: how a ziadatel attaches files in the ticket chat; a ticket without a client answers `409 no_client`, an unreadable one `404`). A file unreadable to the caller answers `404 not_found` on download and preview alike, except that the uploader may always set the preview of their own file; `403 forbidden` is used only for a preview PUT by a reader who is not the uploader.

Task policy lives in `modules/tasks/policy.ts`: `canUseBoard(actor, groupId, actorGroupIds)` (= `canReadGroup`: read the board, create, edit and move tasks, including with the done circle, clients included), `canManageBuckets` (any admin: create, rename and delete custom buckets, reorder every bucket) `canDeleteTask(actor, task)` (any admin, or the client who created the task) and `canAssignTaskTo(actor, person)` (who can be newly assigned to a task, on create, edit and the AI split: a client of the group or one of its managers for anyone; for an admin actor, the superadmin included, also any other active admin who does not manage the client (owner request 2026-10-18). `person` comes from `getGroupPeopleRoles` in one query; a disabled admin, a client of another group or a ziadatel is no person of the group and answers `400 invalid_assignee`; a ziadatel actor never reaches it, the board answers `404`). Existing assignees are not checked again. A group, task or bucket the caller may not read answers `404 not_found`; `403 forbidden` is only for a readable resource the caller may not change (bucket management by a client, deleting someone else's task). Renaming or deleting a fixed bucket answers `400 fixed_bucket`; moving one is allowed.

Reactions and knowledge items in chat (Phase 28, [design](../superpowers/specs/2026-10-17-phase-28-reactions-and-attachments-design.md)):

- `canReact(message)` (`modules/chat/policy.ts`): whoever reads the channel (`findReadableMessage`; a žiadateľ in their ticket chat too) reacts to a live message; a deleted, missing or unreadable one answers `404 not_found`. `GET /api/messages/:id/reactions` (who reacted) has the same read check.
- `canShareKnowledge(actor, groupId, actorGroupIds)` (`modules/knowledge/policy.ts`) = `canReadGroup`: only admins and the group's clients attach knowledge (`knowledgeIds` on send); a žiadateľ gets `403 forbidden`. `isShareableInto(item, folderVisibilities, targetGroupId, adminGroupId)` (Phase 34 P34-C, replacing Phase 28's `isShareable`; see "Knowledge of the admin group" below): the item is of the channel's group, `public`, and every folder up its tree is public, or an admin-group item marked "Shareable with clients", or anything when the channel is the admin group's; anything else on send is `400 invalid_knowledge_item`, and on display the card has only its id (`available: false`). The chat asks the knowledge module (`shareableItemCards` in `modules/knowledge/chat-items.ts`) and never reads its tables.
- `canAttachWork(actor, groupId, actorGroupIds)` (`modules/chat/policy.ts`, Phase 34) = `canReadGroup`: only admins and the group's clients attach tasks and tickets (`taskIds`, `ticketIds` on send; a žiadateľ gets `403 forbidden`). Each id must be a task or ticket of the channel's group (`attachableTaskCards` in `modules/tasks/attachable.ts`, `attachableTicketCards` in `modules/tickets/attachable.ts`); anything else, including a missing one, is `400 invalid_attachment`. The group's readers read every task and ticket of the group, so one DTO per room is right. A reader of a ticket chat who does not read the group (the initiator) gets `forRequester` (`modules/chat/work-links.ts`): no "Turned into tasks" links, no attached tasks, and only the attached tickets the ticket chat's `readableTickets` rule says they read (`readableTicketIds`); `emitMessage` sends the same copy to the extra rooms. `GET /api/groups/:id/tasks/search` needs the board's readers (`canUseBoard`); `q` on `GET /api/groups/:id/tickets` follows the list's own rules. **In the admin group (P34-D, decision 12)** the channel's readers are admins only, who read everything, so `attachableTaskCards` and `attachableTicketCards` accept any task and any ticket (also one without a client) when the target is the admin group (one `or isAdminGroupSql(target)` in each query), and the chat's knowledge check is `shareableItemCards`, whose `isShareableInto` already takes any item of any group there, admins-only ones and admins-only folders included (P34-C). A client or žiadateľ never reaches it: they do not read its channels (404) and `canAttachWork` refuses them. The cross-client searches are admins only (`requireAdmin`, 403 for anyone else): `GET /api/tasks/search?clients=&q=&after=` (every group, or the chosen ones), `GET /api/tickets/global` with `q` and `clients` / `scope`, and `GET /api/knowledge` with `clients` / `scope=all`.
- `GET /api/messages/:id/knowledge/:itemId`: any reader of a live message, for an item attached to it that is still shareable (`getSharedItem`: no reminders, no chat source, `canEdit: false`); else 404. The item's files are readable to a ticket chat's reader through the file read rule `fileOfAttachedKnowledge` (registered with the ticket chat, never an admins-only file). The knowledge routes themselves stay closed to a žiadateľ.

Knowledge policy lives in `modules/knowledge/policy.ts` (Phase 17):

- `canReadItem(actor, item, actorGroupIds)`: `canReadGroup` on the item's group, and the item is `public` or the actor is an admin. Admins-only items are visible to every admin (not only managers). An unreadable item answers `404 not_found`, exactly like a missing one, in the detail, the edit, the delete and the reminder endpoints; the tab's list filters clients to `visibility = 'public'` in SQL, so search cannot reach a hidden item either.
- `canEditItem(actor, item, actorGroupIds)` = `canDeleteItem`: a readable item, and the actor is an admin or its author. A readable item the actor may not change answers `403 forbidden`. A chat file (`chat_file`, Phase 25) is never editable or deletable (403 for everyone; the draft schema has no such type, so `POST` is 400); it goes when its message is deleted in the chat. `canConvertChatFile` (owner request 2026-10-17): its author or an admin, while they read it, may turn it into a file item (`POST /api/knowledge/:id/to-file`); the detail carries it as `canConvert`.
- Chat files (Phase 25, `modules/knowledge/chat-files.ts`): every chat of a group (the group chat, its task chats, its ticket chats) is read by all admins and the group's clients (a client reads every task and ticket of their group), exactly the readers of the group's public knowledge, so a chat file is a `public` item of the chat's group (`chatFileVisibility`, the one place to change should an admins-only chat appear). A ziadatel, also a ticket's own initiator, never reads knowledge (404, no group room). A ticket chat moved to another client moves its entries in the same transaction, so the old client's lists, search and detail no longer reach them.
- `canSetVisibility(actor, item, visibility)`: `admins` needs an admin actor and an admin author (`item` is null on create, where the author is the actor). A client's own item always stays public: a client cannot create an admins-only item and an admin cannot make a client's item admins-only (`400 invalid_visibility`). An admin's item can switch either way, by any admin.
- Files follow the item: the knowledge service sets `files.admins_only` (`setFilesAdminsOnly`) on the item's files whenever they join an item (true for an admins-only item, false for a public one, so a reused upload never keeps a stale flag) and on all of them when the visibility changes, inside the item's transaction. Files are served with a long private cache, so a client who downloaded a file before its item turned admins-only may still have it in the browser cache. Switching an item to admins-only also drops its non-admin reminder recipients (`pruneRecipientsForAdminsOnly`).
- The global list (`listAllItems`, `GET /api/knowledge`) and `GET /api/knowledge/scope` are for admins only: the service does no actor check there, so the routes use `requireAdmin` (a client gets `403 forbidden`). Without a `clients` filter the scope is `managedGroupIdsOf(admin)` (Phase 18's `managedGroupIds`, the groups the admin actively manages); `[]` means every group. `scope=all` means every group whatever the admin manages (400 with `clients`).
- Folders (Phase 24, `modules/knowledge/folders.ts`): `canReadFolder(actor, folder, actorGroupIds)` is `canReadItem`'s rule (the group's readers see public folders, admins all); seeing a folder is enough to rename, move or delete it. `canSetFolderVisibility`: only an admin makes a folder admins-only (`400 invalid_visibility`). A folder the actor cannot see answers `404 not_found` everywhere, exactly like an unknown id or one of another group: the folder list, `GET /api/groups/:id/knowledge?folder=<id>`, a folder as parent or move target, an item's `folderId` on create or edit, PATCH and DELETE. Everything inside an admins-only folder is admins-only: an item or folder created or moved there becomes admins-only (an item's files and non-admin reminder recipients follow, `pruneRecipientsForAdminsOnlyMany`), an explicit `public` there is `400 invalid_visibility`, and making a folder admins-only cascades to its whole subtree. A client's item stays public, so it cannot go into an admins-only folder and a folder holding one anywhere inside cannot become admins-only (`400 invalid_visibility`). Making a folder public changes only that folder. Deleting a folder moves its contents up instead of deleting them, so a client deleting a folder that looks empty learns nothing of the admins-only things in it. A public item's folder path never shows an admins-only folder (the invariant, and the path builder drops any as defence in depth). Moving an item counts as editing it (author or admin). All folder and item writes of a group run under `lockGroupKnowledge` (a transaction advisory lock on the group) so a move cannot make a cycle and a cascade cannot miss an item moved in meanwhile.
- Realtime: an admins-only item's events go only to the group's admins room (`group:<id>:admins`), which only admin sockets join; a client socket never receives them (see [realtime.md](realtime.md)).

Reminders (`modules/reminders`, Phase 17) have no policy file of their own: each subject kind registers an adapter (`registerReminderSubject` in `subjects.ts`) whose `canRead(actor, actorGroupIds)` and `canEdit(actor)` decide, so a reminder is exactly as visible as its knowledge item (Phase 19: its task). The service takes the actor and enforces it:

- **Reading** a set (`getReminderSet`) and the calendar file (`buildIcs`) need `canRead`; an unreadable subject answers like a missing one (null, so 404). `subscribe` and `unsubscribe` throw `NotReadableError` (404) for it, and `NoReminderSetError` (404 `no_reminder_set`) for a readable subject without reminders.
- **Editing** the times and the added recipients (`replaceReminderSet`) happens inside the owner's write, which has checked `canEdit` already (knowledge: the author and admins).
- **Tasks** (Phase 19, `modules/tasks/reminder-subject.ts`): `canRead` is `canUseBoard` (the group's clients and every admin), and `canEdit` is always true, since everyone who reads a task may edit it; every reminder route checks `canRead` first, so another group's client gets 404. Recipients of a task are never limited to admins (`adminsOnly: false`).
- **Project events** (F15, `modules/projects/reminder-subject.ts`): `canRead` is `canReadProjects` (admins and the group's clients; a žiadateľ and another group's client get 404 on every reminder route), and `canEdit` is always true, as `canEditProjects` is the same rule (decision 8). Recipients are the group's people (`adminsOnly: false`), picked as for a task.
- **Recipients** are explicit: the set's author (`reminder_sets.created_by`: the item's author for knowledge, the person who added the first time for a task; source `author`, always kept, cannot unsubscribe: `400 author_recipient`), people the author or an editor added (`added`) and people who subscribed themselves (`subscribed`). Added people must be readers of the subject's group (`getGroupPeopleRoles`, the `listGroupPeople` condition for many ids in one query, with `isManager`) and, for an admins-only subject, be admins; a person new to the set must also be pickable (`isPickable`: a client or one of the group's managers, as for assignees), while one already on it who has since stopped managing stays, and one already on it who is no longer a person of the group (a removed client, a disabled admin) is dropped quietly on the next save instead of blocking it; at most 50 (`400 invalid_recipient`). Anyone who can read the subject may subscribe, not only the picker's people. Unsubscribing deletes the caller's row whatever its source, so an added person can opt out. When a subject becomes admins-only, `pruneRecipientsForAdminsOnly` drops every non-admin row except the author's.
- **Delivery** reaches every recipient even when their group mode is Off, because each one chose this reminder (ruling of the Phase 17-20 brief); they leave it with "Remind me". `listUpcomingForUser` lists only sets the user is a recipient of, for a client only in their current group (filtered in SQL), and drops subjects they can no longer read.

`GET /api/groups/:id/board/unseen` (the viewer's tasks with an unseen change, which the Tasks tab badge also counts) is for any reader of the group (`canOpenGroup`, the board's check); another group or an unknown one answers `404 not_found`. (`tasks/mine-count` of Phase 20 was removed on 2026-10-17.)

Ticket policy lives in `modules/tickets/policy.ts` (Phase 21). The role passed in is the actor's active role in the ticket's group (`roleIn`: `getMembership`, null for admins, outsiders and removed members):

- `canReadTicket(actor, ticket, role)`: admins read every ticket, also one without a client; in the ticket's group a `client` reads every ticket and a `ziadatel` only the ones where `requester_user_id` is themselves. Everyone else gets `404 not_found` on the ticket, its routes and on `GET /api/groups/:id/tickets` (a ziadatel's list there is narrowed to their own tickets).
- `canCreateTicket(actor, role)`: admins for any group, a `client` in that group (they become the initiator; the `requester*` fields they send are ignored); a ziadatel gets `403 forbidden`, someone outside the group `404`.
- `canEditTicket(actor)`: status, fields and client (`PATCH /api/tickets/:id`, `PUT /api/tickets/:id/group`) are admins only; a reader who is not an admin gets `403 forbidden`.
- `canAssignTicket(actor, ticket, role)`: add or remove riešitelia (`PUT`/`DELETE /api/tickets/:id/assignees/:userId`, `GET /api/tickets/:id/assignee-candidates`): admins, and a `client` of the ticket's group; a ticket without a client admins only. A ziadatel gets `403 forbidden`, an unreadable ticket `404`. The DTO's `canAssign` says it to the web.
- `canBeTicketAssignee(role, ticket, memberRole)`: who can be a riešiteľ: any active admin (any role but `client`), and a `client` of the ticket's group; never a ziadatel, a client of another group or, on a ticket without a client, any client. Someone else answers `400 invalid_assignee`. A move drops the riešitelia it no longer allows.
- `canWatchTickets(actor, role)`: "Watch tickets" of a group (`GET`/`PUT /api/groups/:id/ticket-watch`): admins and the group's clients; a ziadatel `403`, someone outside the group or an unknown group `404`. The setting acts only on the signed-in user.
- `canSplitTicket(actor, ticket, role)`: admins and the group's clients, never a ticket without a client (part 21.5). `POST /api/tickets/:id/task-split` answers an unreadable ticket `404`, one without a client `409 no_client`, a ziadatel `403 forbidden`. `POST /api/groups/:id/tasks/from-ticket` needs the board (`canOpenGroup`) and a readable ticket of that group, else `404`. The ticket DTO's `tasks` (the linked tasks) is filled only for admins and the group's clients; a ziadatel gets `null` and only `taskCount`.
- Task links in a ticket chat: whoever reads a channel but not its group (a ziadatel in a ticket chat) gets its messages without `tasks` (the chat routes' `forReader`, and `emitMessage` sends the extra rooms a copy without them), and may not ask the AI to split one of its messages (`POST /api/messages/:id/task-split` checks `canReadGroup`, `403 forbidden`).
- `canOpenInClaude(actor)` (`modules/ai/policy.ts`, Phase 29): admins only. `POST /api/tickets/:id/claude-prompt` and `POST /api/tasks/:id/claude-prompt` check it before looking the id up, so a client or a ziadatel gets `403 forbidden` for any id, also an unknown one; an admin gets `404` for an unknown id. The prompt carries the whole recent chat and the requester's email, which is why it is not for clients.
- Composer AI text tools and voice input (Phase 28, `modules/ai/text-routes.ts`): `GET /api/channels/:id/ai-tools`, `POST /api/channels/:id/ai-text` and `POST /api/channels/:id/transcribe` first need a channel the caller reads (`actorReadsChannel`, else `404 not_found`). The text tools then need the channel's group (`canReadGroup`: admins and the group's clients; a ziadatel in a ticket chat gets `403 forbidden` and `text: false`); voice input is for every reader of the channel, a ziadatel included. Translate is accepted only where `ai-tools` offers it (the group's eGrant link not on `.sk`; `client` only with a client language), else `400 validation_failed`. Per user, in memory: text 20 a minute and 300 a day, voice 10 a minute and 60 an hour (`429 rate_limited`).
- Description fields' AI text tools and voice input (Phase 33 part P5, `modules/ai/group-text-routes.ts`, registered by `textToolRoutes` on the same core): `GET /api/groups/:id/ai-tools`, `POST /api/groups/:id/ai-text` and `POST /api/groups/:id/transcribe` need `canReadGroup` (admins and the group's clients); a ziadatel, an outsider, a bad id and an unknown group get `404 not_found` on all three (voice too: a ziadatel writes no descriptions). Same prompts, Translate rule and answers as the chat's routes, and the **same per-user limiters**: a call here and one in a chat count against one budget.
- AI text tools and voice input outside a client group (`modules/ai/admin-text-routes.ts`, registered by `textToolRoutes` on the same core): `GET /api/ai/admin/ai-tools`, `POST /api/ai/admin/ai-text` and `POST /api/ai/admin/transcribe` are for admins only (`isAdmin`; a client or a ziadatel gets `403 forbidden`, no session `401`). They run in the admin group (no eGrant URL, so Translate is `400 validation_failed`). Used by the bulk email builder, the notes for Claude and a ticket form without a client. Same prompts, answers and **per-user limiters** as the other routes.
- Knowledge attached to descriptions (Phase 33 part P5, `modules/knowledge/links.ts`): `knowledgeIds` in the bodies of tasks, tickets, projects, events and knowledge items take at most 10 items, each new one shareable into the subject's group now (`isShareableInto`: the group's, public, every folder public, or a shareable admin-group item; else `400 invalid_knowledge_item`); an item already linked may stay. Every writer of those descriptions reads the group, so `canShareKnowledge` holds for them. On every read the cards are checked again (`linkedItemCards` → `shareableItemCards` in the subject's current group): an admins-only, deleted or other client's item (a moved ticket) is `{ id, available: false }`. A ziadatel opens an item linked to the text of a ticket they read through `GET /api/tickets/:id/knowledge/:itemId` (`modules/tickets/knowledge.ts`: ticket readable, has a client, item linked, still shareable; the read-only `getSharedItem`, no reminders, never editable; else `404`), and its files through the file read rule `fileOfTicketLinkedKnowledge` (registered by the ticket chat; never an admins-only or finance-only file).
- `GET /api/tickets/global` is admins only (`requireAdmin`). `GET /api/tickets/mine` lists only the caller's own tickets in groups where they still have an active membership.
- `POST /api/tickets/intake` has no session: the Bearer key (`TICKETS_API_KEY`, compared in constant time) is the credential; no key configured answers `503 intake_disabled`, over 60 calls a minute per IP `429` (counted before the key since 2026-10-18, like the managers webhook, so wrong keys are limited too), a wrong key `401`. The rate limit and the key are checked in the route's `onRequest` hook, before the body (up to 28 MiB, for the base64 `files`) is read. It sends no `Origin`, so the CSRF guard lets it through like any server-to-server call. Optional HMAC signing on top of the key (`EGRANT_TICKETS_SIGNING_SECRET`, see the eGrant webhook signing rule below).
- `PUT /api/egrant/managers` (the eGrant managers webhook, `modules/groups/egrant-managers-routes.ts`) has no session either: its own `EGRANT_MANAGERS_API_KEY`, or `TICKETS_API_KEY` when that is unset (`egrantWebhookKey` in `infra/config/config.ts`; `EGRANT_PROJECTS_API_KEY` likewise for the project webhook of PR #113), through `infra/http/bearer-key.ts` (constant time). Its `onRequest` hook answers `503 intake_disabled` with no key configured, `429` over 60 calls a minute per IP (counted before the key, so key guessing is limited too), `401` for a wrong key, all before the body (16 KiB at most) is read. It adds or removes a **client member** (eGrant's "manager" is the client's own person; owner correction 2026-10-18), through `addEgrantClient` / `removeEgrantClient` (`modules/groups/egrant-clients.ts`) over the groups module's `inviteMember`, `restoreMembership` and `removeMembership`, and changes only the group matched by the instance host. **Security boundary:** an outside system must not mint or change privileged accounts, so an account it creates is always `role = 'client'` (`createUnverifiedClient`), and an email (`findUserByEmail`, exact address, case-insensitive) of an `admin` or the `superadmin` is `422 email_is_admin` for both directions, with nothing changed (`inviteMember`'s own `EmailTakenError` guards the race). It never touches `group_managers`, never re-enables a disabled account (`422 user_disabled` on add) and never disables one (removing the last membership leaves an active client with no group, who sees only their own tickets, like a requester). A deactivated group answers `409 group_inactive` before anything changes.
- `PUT /api/egrant/groups` (the eGrant groups webhook, `modules/groups/egrant-groups-routes.ts`) has no session: the Bearer key is `EGRANT_GROUPS_API_KEY`, or `TICKETS_API_KEY` when that is unset (`egrantWebhookKey(config, 'groups')`), compared in constant time through `infra/http/bearer-key.ts`. Its `onRequest` hook answers `503 intake_disabled` with no key, `429` over 60 calls a minute per IP (counted before the key), `401` for a wrong key, all before the body (3 MiB at most, for a base64 logo of up to 2 MiB) is read. It creates a client group or changes the name, logo and active state of the one matched by host, through the groups service (`createGroup`, `updateGroup`, `replaceGroupLogo` / `removeGroupLogo`, `setGroupActive`). **Security boundary:** it never deletes a group, never touches members, managers or the admin group (which has no eGrant URL), and stores only PNG, JPEG or WebP bytes that sniff as the declared type, with their metadata stripped; an SVG is never stored or served: it is rendered to a PNG by resvg in WebAssembly, which runs no scripts and has no file or network access (ADR 0039). Its log lines carry the group id, the state and whether a logo was sent, never the key, the name or image data.
- **eGrant webhook signing** ([ADR 0042](../decisions/0042-egrant-webhook-hmac-signing.md), `infra/http/egrant-signature.ts`): optional, per webhook, on top of the Bearer key. With `EGRANT_<NAME>_SIGNING_SECRET` set (`TICKETS`, `MANAGERS`, `GROUPS`, `PROJECTS`; at least 32 characters, `config.egrantSigningSecrets`), the route also needs `X-Spolu-Timestamp` (unix seconds, within ±300 s) and `X-Spolu-Signature: sha256=<hex>` = HMAC-SHA256 over `"<timestamp>.<raw body>"`, compared in constant time; a signature already taken inside the window is a replay. Any failure is `401 unauthorized`. Order: the `onRequest` gate (`503 → 429 → 401` key) stays first; then `preParsing` checks the headers and the clock before the body is read and hashes the body as Fastify reads it (the route's `bodyLimit` still applies; no copy is kept); then `preValidation` compares the digest and checks the in-memory replay cache before the handler. Unset: the headers are ignored and the route is unchanged. Each route opts in with one line in its options, `...egrantSignature(config, '<webhook>')`: the intake, the managers and the groups webhooks do; the projects webhook (PR #113) adds it with its PR.

Unseen changes (2026-10-17): `POST /api/tasks/:id/seen` needs `canUseBoard` for the task's group (as `GET /api/tasks/:id`), `POST /api/tickets/:id/seen` `actorReadsTicket` (as `GET /api/tickets/:id`), and `GET /api/groups/:id/board/unseen` the board's own check; otherwise 404. `GET /api/tasks/:id/unseen-summary` and `GET /api/tickets/:id/unseen-summary` (2026-10-18) check the same as their `seen` route, at the time of the request, so a ticket moved to another client answers 404 to its old one. Each writes or reads only the caller's own seen marks and events. `POST /api/projects/:id/seen` (2026-10-18, the Mentions card's mentions in descriptions) needs `canReadProjects` for the project's group (as `GET /api/projects/:id`), and `POST /api/knowledge/:id/seen` `canReadItem` (as `GET /api/knowledge/:id`, through `canReadItemById`); otherwise 404 and nothing is written.

The admin home (`modules/home`, Phase 20) has no policy file: every route is admins only through `requireAdmin` (a client gets `403 forbidden`, no session `401`): `GET /api/me/home/sidebar`, `GET /api/me/home/tasks`, `GET /api/me/home/tickets` (admins read every ticket, so no ticket policy check applies), `GET /api/me/home/counts`, `GET /api/me/home/mentions` and `GET /api/me/home/reminders` (the reminder source lists only sets the admin is a recipient of, through the reminders service). `GET /api/tasks/global` (the global task board) is admins only too and needs no per-group permission filter, because admins read every group; a bad filter or cursor answers `400 invalid_filter`. Admins read every group, so no per-group filter applies; each answer is about the caller (`request.user`) only. The one exception is the mentions card: a ticket chat's message, and (2026-10-18) a mention in a ticket's text, is kept only while `readableTicketIds` (`modules/tickets/service.ts`, `canReadTicket` for the listed tickets in one batch) says the caller reads its ticket, so a card item never opens a not-found page.

- `POST /api/auth/ticket-link/sign-in` has no session: the token of a "Ticket created" email is the credential ([ADR 0022](../decisions/0022-one-click-ticket-sign-in-link.md)). It signs in only a žiadateľ: role `client`, not deactivated and no active `client` membership of any group (`clientGroupIds`), checked when the link is made and again when it is used; an admin's or a group client's link never exists and a stale one is refused. It creates an ordinary session of that user and nothing more; the ticket itself is then read through `canReadTicket` as usual.

Who is calling comes from the session cookie, read in `modules/auth/session.ts`. Routes use the preHandlers `requireUser(app.auth)` (no valid session: `401 {"error":"unauthorized"}`) or `requireAdmin(app.auth)` (no session: 401; not `isAdmin`: `403 {"error":"forbidden"}`); both set `request.user` (`SessionUser`). A disabled user counts as logged out even if a session row still exists. Finer checks (which group, which admin) call the module's policy functions with `request.user` before the service. State-changing requests from another site are refused earlier by the CSRF guard (see [overview.md](overview.md), "CSRF guard").

Notification settings (`modules/notifications/routes.ts`) are about the signed-in user only: every handler acts on `request.user`, and there is no route that names another user. Any signed-in user reads and changes their own preferences and push subscriptions (a `DELETE` of someone else's endpoint deletes nothing and still answers 204). A user sets a per-group mode only for a group `canReadGroup` allows, otherwise `404 not_found`. Only an admin sets the all-groups default mode (`PUT /api/notifications/modes/default`, a client gets `403 forbidden`); setting it also deletes that user's per-group overrides. The effective mode is the per-group override, then the user's default, then the role default (client `all`, admin `mentions`).

The profile routes (`modules/auth/routes.ts`) change only the signed-in user themselves: `PATCH /api/me` (name), `PUT /api/me/language`, `POST /api/me/email-change` and `POST /api/me/email-change/confirm` act on `request.user` and take no user id, so no one, not even a superadmin, changes another user's name, language or email there. An email-change request is stored under `email-change:<userId>` and holds the new address, so a code confirms only its own user's change to that one address; anyone else confirming it gets `400 invalid_code`. The superadmin cannot change their email and no one can take `SUPERADMIN_EMAIL` (`400 validation_failed`), because `ensureSuperadmin` keys the superadmin on that address; it also never promotes an existing admin or client row.

Policy functions are written test-first. Confirmed in Phase 3: reading a resource you may not read answers 404, the same as a missing one.

## The admin group (Phase 34, P34-B)

The admin group "eGrant tím" is one `groups` row with `kind = 'admin'` ([ADR 0029](../decisions/0029-admin-group-as-a-group-row.md)). `canReadGroup` is unchanged: every admin reads it, as every group; no client and no requester has a membership of it, so none reads it, over HTTP or sockets (`group:join` answers `not_found`). Each rule below is one call in its module (`isAdminGroup` in `modules/groups/admin-group.ts`, `canHoldTickets` in `modules/tickets/policy.ts`):

- **No members, invites or managers.** `POST /api/groups/:id/invite`, `POST /api/groups/:id/members`, `GET …/members/invited`, `DELETE …/members/invited/:userId`, `GET …/members/removed`, `DELETE …/members/:userId`, `POST …/members/:userId/restore`, `GET …/requesters`, `GET …/requesters/removed` and the four manager routes answer `409 admin_group`; `GET …/members` answers `404` (there is no Members tab). There is no group delete route, so it cannot be deleted.
- **Pickable people.** In the admin group every active admin is pickable (assignee, mention, reminder recipient): `listGroupPeople`, `listPickablePeople` and `getGroupPeopleRoles` report `isManager` true for every admin there, so `isPickable` and every caller work unchanged. In client groups the rule stays "its clients and its active managers", except that an admin assigning a task may also pick any active admin (`canAssignTaskTo`, 2026-10-18); mentions, @all and reminder recipients keep the rule.
- **No tickets.** Creating a ticket there or moving one into it answers `400 invalid_group` (the route, and `createTicket` once more for any caller); `GET /api/groups/:id/tickets` and both ticket-watch routes answer `404`. The intake never matches it: it has no eGrant URL, and `findGroupByEgrantUrl` ignores null.
- **Default scopes.** The global board's and the knowledge list's default "my clients" scope (`resolveClientIds`, `managedGroupIdsOf`) add the admin group when the admin manages any client (every admin is effectively its manager); an admin who manages none already sees every group. `GET /api/knowledge/scope` returns the same list.
- **Notifications.** Its effective mode falls back to All messages before the user's default and the role default (`effectiveGroupMode` with `adminGroup`, `getEffectiveModes`, `groupModeSql`); a per-group choice (the bell) still wins.
- **AI.** Translate is never offered there (no eGrant URL, so no foreign domain); Fix and Formal are.

### Knowledge of the admin group (Phase 34, P34-C)

One rule decides every attach check and every display re-check, in chats (`checkKnowledgeIds`, `loadMessageKnowledge`) and descriptions (`setLinkedItems`, `linkedItemCards`), through `shareableItemCards` (`modules/knowledge/chat-items.ts`): `isShareableInto(item, folderVisibilities, targetGroupId, adminGroupId)` in `modules/knowledge/policy.ts`.

An "Only eGrant" (`admins`) item, one inside an "Only eGrant" folder and another client's item are `400 invalid_knowledge_item` on save and `{ id, available: false }` on display, so switching an item back, moving it into an "Only eGrant" folder or deleting it closes every card at once.
- **Into the admin group:** any item of any group, any visibility (decision 12: its readers are admins, who read everything).
- **Defaults.** A new item of the admin group is "Only eGrant" unless the body names a visibility (`POST /api/groups/:id/knowledge`); a file sent in its chats becomes an `admins` chat-file item (`chatFileVisibility`). Migration 0042 turned every earlier public admin-group item (and its attached files) "Only eGrant", so nothing became shareable without the conscious switch.

Each returns `getSharedItem`: no reminders, never editable, and no folders (`folderId` null, `folderPath` empty) for an item of another group. Cards carry `source: 'admin_group'` and no folder path.
- **Files.** The file read rules open a shared item's files to the readers of the place: `fileOfAttachedKnowledge` now checks every chat kind (a client in a group or task chat does not read the admin group's files otherwise), and `fileOfLinkedKnowledge` (`link-routes.ts`) covers task, project, event and knowledge descriptions; `readableByRule` still never opens an admins-only or finance-only file.
- **The picker.** `GET /api/groups/:id/knowledge?shareable=1&source=admin_group` lists the admin group's shareable items, **for admins only** (a client gets `404`): a client never browses the team's knowledge, they only open what an admin attached in their place.

## MCP server (2026-10-18)

[ADR 0033](../decisions/0033-mcp-server-over-the-http-api.md), [spec](../superpowers/specs/2026-10-18-mcp-server-design.md). Policy functions in `modules/mcp/policy.ts` (test-first):

| function | rule |
|---|---|
| `canUseMcp(actor)` | admins and the superadmin (v1): make, list and revoke their own tokens (`/api/me/mcp/*`, `requireAdmin` then this; a client or a žiadateľ `403`) and call `/mcp` (a token whose user is no longer an admin `403`) |
| `canCallTool(actor, scope, tool)` | a write tool needs a `write` token; a finance tool needs `canSeeFinance` |

- **Identity.** A token acts as its user and nothing more: every tool calls the `/api` routes in process as that user (`app.inject` with the internal-call header), so each route's guard, policy functions and `404`-for-unreadable answers apply unchanged. The user is read fresh on every `/mcp` request (`authenticateToken`: not revoked, not expired, user not disabled, role and finance right from the row). A revoked, expired or unknown token and a deactivated user answer `401`; deactivation also revokes every token (`deactivateUser` calls `revokeAllTokens`).
- **The internal-call header** (`x-spolu-internal-call`) is honoured only by `getSessionUser` and only for an id registered in this process for the duration of one call (`runAsUser`); from outside it is no session (`401`). `GET /api/me` and the other auth routes read the cookie only, so they are not reachable from MCP.
- **Allowlist.** `modules/mcp/allowlist.ts` lists every method + path the MCP layer may call (deny by default; `RouteNotAllowedError` otherwise). It holds no `/api/me/mcp/*`, auth, finance-grant, upload or delete route (the only `DELETE` is unassigning a riešiteľ). Checked twice: `createApiCaller` matches the concrete path against each entry's regex before the call, and the route guard (`modules/mcp/guard.ts`, an `onRequest` hook on the root app) refuses (`403`, `detail: "route not allowed for MCP"`) every internal call whose resolved route (`request.routeOptions.url` + method) is not exactly an entry, so a static sibling such as `GET /api/tasks/search` next to `GET /api/tasks/:id` stays unreachable.
- **Scope per call.** `createApiCaller` gets the token's scope: a `read` token's caller sends `GET` only (any other method throws `RouteNotAllowedError`), as defence in depth behind `canCallTool`.
- **Finance** (owner decision 2026-10-18: full access, read and write, mirroring the HTTP API, no deletes). Every finance and `/time` entry of the allowlist is marked `finance`, and `isAllowedRoute` refuses it before the route to anyone without `canSeeFinance`; this covers the organisation level too (`/api/finance/org/items`, `/api/finance/org/folders`, `/api/finance/payees`: contracts of several clients with their shares, expenses, salaries); a client's view of a shared contract (`groupId` on `list_finance_documents` and `get_finance_document`) is the route's own (`sharesVisibleIn`), only that client's share. Every finance tool is `finance` too, so a non-finance admin sees none in `tools/list` and gets `403 forbidden` from each. The task and ticket time tools are finance-only as well, stricter than the HTTP routes (which let an assignee without the right log their own time). The general tools drop `askTime` and the "Fill in your time" requests, so time and money come only from finance tools.
- **Read-only tokens** list no write tool; a write call is a tool error `403 forbidden` (`detail: "read-only token"`), audited, and changes nothing.
- **Audit.** Every write tool call, also a refused one, writes `mcp_audit_log` (user, token, tool, target id, status, ok, time; never content). `GET /api/me/mcp/audit` shows a user only their own last 50. Rows older than 180 days are deleted daily (`mcp.cleanup-audit`).
- **New-token notice.** Making a token emails its owner (name and time, "if this wasn't you, revoke it in Settings"; never the token), so a token made with a stolen session is noticed.
- **Other checks of `/mcp`.** An `Origin` other than `PUBLIC_URL`'s answers `403`; 120 requests and 30 writes a minute per user (all their tokens together; each message of a batch counts), 30 failed authentications a minute per IP (`429`; an address over it is refused before the token lookup, so for the rest of that minute a good token from it waits too); the routes' own per-user limits apply on top. JSON-RPC batches only in protocol `2025-03-26` (also assumed without the `MCP-Protocol-Version` header), at most 10 messages; the answer to one POST is at most 5 MB.
- **OAuth connections** ([ADR 0034](../decisions/0034-mcp-oauth-authorization-server.md), [spec](../superpowers/specs/2026-10-18-mcp-oauth-design.md)). Claude's custom connectors get access tokens through Help's own OAuth server; each is an `mcp_tokens` row of a connection, so everything above applies to it unchanged (identity, scope, the read-only caller, allowlist, finance, audit, per-user limits). Approving is `canUseMcp` again (consent page, `GET`/`POST /api/oauth/authorize`: `requireAdmin` then `canUseMcp`; a client or a žiadateľ `403`) and emails the owner like a new token; every code exchange and refresh re-reads the user (disabled or no longer an admin: `invalid_grant`), and deactivation revokes every connection. A connection's scope is chosen on the consent screen and can never exceed what the client asked for, nor be widened by a refresh. Codes reach only registered addresses on `claude.ai`, `claude.com` or loopback; an unknown client or address is never redirected to. The approval needs the consent token (HMAC over the login session and the parameters) besides the `/api` Origin guard. A reused code or refresh token revokes its connection. `GET`/`DELETE /api/me/mcp/connections` act on the caller's own connections only (another's `404`). None of these routes is in the allowlist.
- Tests: `modules/mcp/policy.test.ts`, `oauth.test.ts`, `tokens.test.ts`, `routes.test.ts`, `transport.test.ts`, `audit.test.ts`, `leaks.test.ts` (the allowlist against the registered routes, the exact route match, the read-only caller, finance per role, no other client's data in a client's finance answers, only a client's own share of a shared contract), `tools.test.ts`, `events.test.ts`.

## Deactivated groups (2026-10-18)

A client group with `deactivated_at` set ([product/groups.md](../product/groups.md#deactivating-a-group-2026-10-18), [ADR 0038](../decisions/0038-egrant-groups-webhook-and-group-deactivation.md)):

- **Clients and requesters read nothing of it.** The membership readers (`clientGroupIds`, `activeRolesIn`, `listMemberships`, `activeMemberOfSql`, `activeMemberIdsSql`, `hasActiveRoleSql`, `activeGroupNamesSql` in `modules/groups/memberships.ts`; the tickets' `roleIn` goes through `activeRolesIn`) ignore memberships of a deactivated group, so every `canReadGroup`, `canUseBoard`, `canReadTicket` and socket check answers not found, with no change in the modules. Their accounts are untouched. The invite token opens nothing (`getGroupByInviteToken`).
- **Admins read it**, through the unchanged `canReadGroup`, and are the only ones who change its state: `POST /api/groups/:id/deactivate` and `POST /api/groups/:id/reactivate` need `canManageGroups` (`403` otherwise; `404` unknown; `409 admin_group` for the admin group) and answer the group. The webhook's `active` uses the same `setGroupActive`.
- **Nothing new is written in it, by anyone**: the database triggers refuse new messages, tasks, buckets, tickets (and moving one in), knowledge items and folders, projects, project events and reminder sets with SQLSTATE `SPG01`, which the app's error handler answers `409 group_inactive`. The groups routes refuse a new invite link, adding members and restoring a member with `409 group_inactive`. Edits of existing rows and finance stay allowed for admins.
- **Integrations**: the ticket intake and the managers webhook answer `409 group_inactive` for its instance and store nothing.
- **Lists**: `GET /api/groups` leaves it out unless `?deactivated=true` (then only deactivated groups), so every picker and the MCP `list_groups` skip it; the admin sidebar, the global board, the task search across groups and the global search (every type, admins too) leave it out too. So does Home (review V5): the Assigned to me and Tickets cards, the header's Tasks and Tickets counts, the Meetings card and the upcoming reminders (list and count) filter on `g.deactivated_at is null` or `liveGroupSql` (`modules/groups/memberships.ts`, true for a ticket or reminder without a client).
- **Pending invites**: an invite the person typed their email on before the group was deactivated is dropped at sign-in without a membership (`applyPendingInvite`, review V6), so reactivating the group later does not make them a member.
- **Notifications**: `recordManyNotifications` records nothing for it; `stopGroupNotifications` marks its pending events delivered and emailed when it is deactivated.

## Global search (2026-10-18)

[Spec](../superpowers/specs/2026-10-18-global-search-design.md), [ADR 0046](../decisions/0046-global-search-module-functions-and-fold-index.md). `GET /api/search` needs a session (`requireUser`, any role; `401` without). The search module reads no table itself: each type is its module's exported search function, which scopes its one query by the module's own policy and then filters every returned row with that same policy (`groups/search.ts` `canReadGroup`, `tasks/search.ts` `canUseBoard`, `tickets/search.ts` `canReadTicket` with the caller's role in the ticket's group, `knowledge/search.ts` `canReadItem`, `projects/search.ts` `canReadProjects`). The caller's roles come from one read of their active memberships (`groupAccessOf` in `groups/memberships.ts`; admins skip it).

- **Admins** find every group (the admin group too), ticket (also without a client), task, knowledge item (admins-only ones too), project and event.
- **A client** finds their client groups and every ticket, task, project and event of them, and their public knowledge items; never another client's, the admin group's or a ticket without a client.
- **A žiadateľ** finds only the tickets they started, in groups where their membership is active.
- **People** (`users/search.ts`) only for admins: `canSearchPeople` in `users/policy.ts` (`isAdmin`); for anyone else the `people` list is absent from the answer.
- **Deactivated groups: nothing of them, for anyone** (owner decision of 2026-10-18). `groupAccessOf` ignores memberships of a deactivated group (`inLiveGroup`, like every membership reader), so its clients and žiadatelia read nothing of it; and every search function adds `groups.deactivated_at is null` on the group it joins, for admins too: `groups/search.ts`, `tasks/search.ts`, `tickets/search.ts` (a ticket without a client stays), `knowledge/search.ts`, `projects/search.ts` (projects and events). A person hit (admins) is still listed, but `firstActiveGroupSql` skips a deactivated group, so it never links into one. The MCP `search` tool calls the same route. Tested in `modules/search/routes.test.ts` ("a deactivated group", over HTTP and MCP).
- **Finance never:** no search function reads a finance table, so a finance item never appears, for finance admins either. Chat files and messages are not searched.
- 120 searches a minute per user (`429 rate_limited`). The MCP `search` tool calls the same route (allowlisted).

The leak matrix is `modules/search/routes.test.ts`.
