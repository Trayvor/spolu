# Performance

Spolu must feel instant: faster than Microsoft Teams on a cheap phone over mobile data, served from a small server. Performance is a top priority (see [product/non-functional.md](../product/non-functional.md)), but **readable code comes first**. A rule here is never a reason to write clever or obscure code.

## Why Spolu can be fast

- A plain web app (PWA), not a desktop wrapper. Code loads once, then runs from the browser cache.
- Each screen is its own lazy-loaded chunk: opening the chat never downloads the task board.
- Hashed `/assets/*` files are cached forever (`immutable`); `index.html` is always revalidated, so updates arrive at once.
- Realtime is pushed over one WebSocket. Nothing polls.
- One Node process next to PostgreSQL: a request crosses no extra services.

## Rules for every phase

### Web client

- Lazy-load every route (screen). Shared code used by one screen stays in that screen's chunk.
- Feature texts are lazy locale namespaces (`src/locales/<name>/<code>.json`), loaded with the route that renders them (`withNamespaces` in `router.tsx`, see [overview.md](overview.md), "i18n"). Only the eager shell's texts go in the main locale files.
- Before adding a dependency, check its gzip size (bundlephobia or the build output). Prefer a few lines of our own code to a large library used for one function. A new runtime dependency needs an ADR anyway.
- Lists that grow (messages, tasks, tickets, members) are paginated by cursor and virtualized when long. Never load a whole list.
- A list with filters remembers them with `useRememberedFilters(list, keys, search)` (`lib/use-remembered-filters.ts`; `useRememberedState` for a filter kept in component state). The URL stays the source of truth: filter params in the URL are used and saved; a list opened without any gets the saved ones written into the URL with `replace`, and the hook already returns them on the first render, so the first request is the right one (no default fetch first). Saved per user in `localStorage` under `spolu.filters.<userId>.<list>`, the list key carrying the group id where filters are per group; every access is in try/catch. Free text search is never a remembered key. Emptying the filters (a "Clear filters" button) forgets the saved value. A new list with filters uses the hook; `src/test/setup.ts` clears the saved filters before each test.
- A socket (re)join or `connect` refetches only what may have missed events: use `firstJoinCheck` (`lib/socket-history.ts`, see [realtime.md](realtime.md)) so the first join of a screen does not refetch what its mount just loaded. Measured in the hooks' tests (Phase 27, W4): a cold load of the Tasks tab sends 1 board request instead of 2 (the second also invalidated every cached task detail), the Knowledge tab 1 list request instead of 2 (plus the folders), and the ticket and bulk email lists 1 instead of 2 when the socket connects after they loaded.
- Optimistic UI for the user's own writes (a sent message appears at once, then is confirmed).
- Images: resized and compressed on upload; lists and chat show thumbnails; full size only on open.
- No fancy effects (see [design/README.md](../design/README.md), "Keep it light").
- The service worker precaches what most devices use: every script except the seven lazy languages' texts, which are cached on first use (`apps/web/pwa-precache.ts`). Phase 27: 307 files and 759 kB gzip down to 167 files and 613 kB.

### Server and database

- Every column used to filter, join or sort has an index. Add it in the same migration as the query.
- Every foreign key column leads an index too, or deleting a parent scans the child table once per deleted row (`infra/db/foreign-key-indexes.test.ts` checks it; see [data-model.md](data-model.md)).
- No N+1: load related rows with one join or one `in (...)` query, not one query per row.
- The app's connections run with PostgreSQL JIT off (`connection: { jit: 'off' }` in `infra/db/client.ts`). Spolu sends short statements. The planner's cost estimates for the ones with correlated subqueries (global board, admin sidebar) pass `jit_above_cost`, and compiling them cost more than running them. Phase 27 measured, on the seeded volume: the global board of an admin who manages no client took 720 ms with JIT and 100 ms without (924 ms of a 1 110 ms `EXPLAIN ANALYZE` was compilation); the sidebar with 3 100 groups took 350 ms and 125 ms. The database server keeps its default; pg-boss's own connections are not changed.
- Endpoints return only the fields the screen needs, and every list endpoint is paginated.
- Realtime events carry small payloads (ids and changed fields) and go only to the rooms that need them.
- Slow work (emails, file processing) runs in pg-boss jobs, never inside the request. Bulk email sending (Phase 23.5) is the `bulk-email.batch` job: one worker, 20 people a run with `for update skip locked`, one `insert … select` freezes the recipients, one query per batch for image sizes, one update per person before and after their call (so a crash never resends), runs spaced by `BULK_EMAIL_PER_MINUTE`; the send request returns at once. The report list is keyset-paged by `(name, user_id)` within one campaign; the counts are one grouped query per campaign page. One exception: the AI task split (`POST /api/messages/:id/task-split`) calls OpenAI inside the request, because the user waits on the review screen for the answer; the call has a 30 s timeout, no retry, and holds no database transaction or connection while it waits.

The budget is an **alarm, not a target to squeeze under**. When a change crosses it:

1. Find what grew (the build prints chunk sizes).
2. Fix it the normal way: lazy-load the screen or component, drop or replace a heavy dependency, or move code out of the entry chunk.
3. If the growth is justified (a real feature needs it), raise the budget in this file with a one-line reason in the same commit. That is a legitimate outcome.

Never do this to fit the budget: minify or obfuscate by hand, inline or copy library code, drop types or tests, merge unrelated code into odd places, or remove useful features. A reviewer rejects such code even when it fits.

## How to check

- `pnpm --filter @spolu/web build` prints every chunk with its gzip size (Vite's default gzip level, a little above the budget's numbers).
- The budget's number is gzip -9 of every script `dist/index.html` loads (the module, its modulepreloads and `registerSW.js`), in kB of 1000 bytes. After the build:

  ```bash
  cd apps/web/dist && grep -oE '(src|href)="/[^"]+\.js"' index.html | sed -E 's/.*="\/(.*)"/\1/' | sort -u \
    | while read -r f; do gzip -9c "$f" | wc -c; done | awk '{ s += $1 } END { printf "%.2f kB\n", s / 1000 }'
  ```

  Compare with the same command on `origin/main` and write the result here when it changes.
- Lighthouse in Chrome DevTools (mobile, throttled) on the test server: aim for Performance 90+ on the home screen.

## Test suite speed

`scripts/ci.sh` takes about 13 minutes on GitHub (Phase 27): unit and integration tests 7 minutes (the server and web suites run in parallel), e2e 4.7 minutes. Lint, format check and typecheck are independent, so `ci.sh` runs them at the same time (`run_parallel` in `scripts/lib.sh`, Phase 27 T5): on GitHub they took 71 s one after another (29 + 15 + 27 s). Measured locally on a loaded 8-core laptop (two rounds each, same tree): 27 to 55 s one after another, 18 to 28 s in parallel, so about 10 to 27 s saved per run; on the 4-vCPU runner the expected saving is about 30 s (the PR's GitHub run gives the real number). e2e stays serial: its tests share one database. The web suite runs Vitest's `vmThreads` pool (`apps/web/vitest.config.ts`): every file still gets its own VM context, but workers and their jsdom are reused. With the default `forks` pool jsdom was set up once per file, a third of the run: 31 to 44 s locally, 13.5 to 17 s with `vmThreads`, all tests passing. The server suite keeps `forks`: under `vmThreads` (34 s to 24.5 s locally) a time-based reminder test failed under the extra load, so that switch waits until the load-sensitive tests are fixed (Phase 27 findings, T2 and T3).

### No wall-clock budgets in CI tests

Tests run on machines with a load average of 30 or more (many parallel runs), so a test that asserts "this took less than N ms" fails for reasons that have nothing to do with the code. The rule: **no wall-clock assertions in CI tests, not even ratios of two timings; use counts, fake timers or opt-in benchmarks.** Every wall-clock check runs only with `RUN_BENCH=1`, which `bash scripts/ci.sh --bench` sets (default off; CI never passes it). Run it on a quiet machine after touching the parser or an index.

- **Linear-time guard** (the chat parser on hostile input, `features/chat/format/parse.test.ts`) is a benchmark (`it.runIf(import.meta.env.RUN_BENCH)`): the same input at size N and at 8N, best of five, and the ratio must stay under 32 (linear is about 8, quadratic about 64). Even a ratio flaked: in a full `ci.sh` it reached 32.8 for `'*'.repeat(n)`. Measured on a quiet machine (2026-10-17, best of seven) the parser is linear: 0.9, 1.8, 3.4, 6.9, 14.0 ms for 12k, 24k, 48k, 96k, 192k `*`; `_`, `~`, backticks and mixed marks double the same way.
- **Query plans** (`modules/home/explain.test.ts`, `modules/finance/explain.test.ts`) always assert "no sequential scan of these tables", on the first seeding (no `retry`). The 50 ms bounds run only with `RUN_BENCH=1`.
  A plan check must pass on the first seeding of the fresh `_explain` database. A rolled-back seeding leaves its rows as dead tuples, so a second seeding in the same database sees `messages` at twice its pages, and the planner prices a sequential scan twice as high. That is how `retry: 2` once hid the mentions query's sequential scan of `messages` (2026-10-17): the planner hashed the admin's 1 000 mention candidates against a parallel scan of the 200 000 messages, because its cost model put that below 1 000 primary-key lookups, which run several times faster on a warm cache. The fix was in the query, not the volume: each candidate now reads its message in a `lateral` subquery with `offset 0`, which the planner does not flatten into a join, so the lookup always goes through `messages_pkey`.
- **N+1 and batching guards** count queries (`test/query-counter.ts`), never time.
- **Debounces** ("asks once, 300 ms after the last change") use fake timers (`vi.useFakeTimers` and `advanceTimersByTimeAsync`, as `bulk-email/audience-builder.test.tsx` and `tasks/tasks-tab-badge.test.tsx`): with real timers two clicks on a loaded machine can be more than 300 ms apart.
- **Jobs and pushes** assert ordering or overlap (`queues.test.ts`, the `localConcurrency` peak in `jobs.test.ts`), not latency.
- **Waiting for something that must happen** (a job, a socket event, an email) polls with a generous deadline (25 to 30 s) and a per-test timeout above it. The deadline only bounds a hang; it is not a budget. Vitest's `testTimeout` and `hookTimeout` are 15 s in both apps, and Testing Library's `asyncUtilTimeout` is 5 s (`apps/web/src/test/setup.ts`). Timeouts stay finite, so a real hang still fails.
- A real benchmark goes into an opt-in file (behind `RUN_BENCH=1` or a `*.bench.ts` run with `vitest bench`) that CI does not run.
