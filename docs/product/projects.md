# Projects (Phase 33)

Requirements as built. Design: [Phase 33 spec](../superpowers/specs/2026-10-17-phase-33-projects-design.md) (its "Owner decisions" first), [plan](../superpowers/plans/2026-10-17-phase-33-projects.md). Built in six parts; each part fills its own section below.

## Concepts

- **Project** (sk "Projekt"): belongs to one client group. Name (1–200, required), description (Markdown, ≤ 10 000), files (0–20 ordinary group files), status **active** or **archived**, source **manual** or **egrant** ("From eGrant"), eGrant's project id (read-only), **aliases** (the name keys of its earlier names).
- **Event** (sk "Udalosť"): belongs to one project. Name (1–200), description, files, **date** (one day, required, past dates allowed). Events of one day are ordered by creation.
- A task or a ticket has at most one project and, inside it, at most one event (part P2 sets them). The database refuses another client's project and an event of another project ([ADR 0030](../decisions/0030-projects-composite-keys-and-egrant-matching.md)).
- Each project has a **colour** from the brand accents (purple, pink, blue, coral, green), picked by a hash of its id like avatars; shown only as a small dot.
- **Name key**: the name trimmed, inner spaces collapsed, lower-cased, without diacritics. Two projects of one client never share a name key; a rename keeps the old key as an alias ("Also matches"), which anyone who edits the project can remove.

## Who sees and does what

Admins and the group's clients (everyone who reads the group) see projects and events and **create, edit, archive, restore and delete** them, add files, and remove aliases (decisions 8 and 8a). A žiadateľ never reaches the group, so every project route answers them `404`; on their own ticket they will see only the project's name (part P2). Details: [permissions](../architecture/permissions.md#projects-phase-33).

## Foundation (part P1)

- **Prehľad tab** (EN "Overview"), `/groups/<id>/overview`: the **first** tab pill of a group; a group opens on it: the bare `/groups/<id>` redirects here (links that name a tab, such as `/chat`, keep that tab). It is one lazy chunk (`overview-tab`) with the `projects` locale namespace. Part P4 adds the timeline above and the two active cards in the middle; P1 shows the projects card.
- **Projects card**: the client's projects by name, 30 a page with "Show more", **Active** or **Archived** (pills, remembered per person and client). Each row: the colour dot, the name, "From eGrant" for eGrant's projects, "eGrant changes (n)" (from part P3), then the number of events, the next coming event (from today, Bratislava) with its date, and the open tasks and open tickets (shown only when there are any). Empty: "No projects yet. Projects group this client's tasks and tickets along a timeline." "New project" opens the project dialog; a row opens the project sheet.
- **Project sheet**: name with its dot, "Archived" and "From eGrant" badges, the description (rendered Markdown), files, and the **events** by date with "Add event". The menu has Edit, Archive or Restore, and Delete. Delete asks first and names what happens: its events go too; its open tasks and tickets stay, without the project. Clicking an event opens it in the event dialog.
- **Project dialog**: name, description (the description editor with AI, voice and attached knowledge, part P5), files; for an existing project the **Also matches** chips (aliases, each removable) and the eGrant project id (read-only). A taken name says which project has it; an edit made by someone else meanwhile asks to reopen (`409 project_changed`).
- **Event dialog**: the project (fixed), name, date, description, files; an existing event can be deleted there after a confirmation (its tasks and tickets keep the project).
- **Archive** is the normal way to end a project: it leaves the active list and the pickers' active section, stays in the Archived list and stays selectable for tasks and tickets. **Delete** removes the project, its events, files, aliases and links; its tasks and tickets keep existing without it. Deleting an event clears only the event on its tasks and tickets.
- **Live**: every write tells the group's room `project:changed`; an open Prehľad refetches 2 s after the last change.
- Merge ("Merge into…") is part P3's. "Show on the timeline" (part P4, in the sheet's menu) selects the project in the timeline.
- **The admin group** "eGrant tím" (Phase 34, `kind = 'admin'`) has the Prehľad tab and its own projects too: the project routes check `canReadGroup`, which only admins pass there. Its card counts no tickets (the admin group has none); the eGrant webhook and ticket links (part P3) concern client groups only.

## Links and filters (part P2)

Built (part P2, `feat/projects-links`).

- **Tasks:** the task form (new task, task panel, the AI review cards) has a **Project** select ("No project", then the client's active projects by name; an archived project shows only while it is the task's) and, once a project is chosen, an **Event** select ("No event", the project's events with their dates, coming ones first, then the past ones). Changing the project clears the event. Both load when the form opens (one small cached request each; a native select opened before its options arrive would not show them). Cards on the group and global boards show a **chip**: the project's colour dot and name, ", event" when set, truncated.
- **Tasks from a ticket** (Turn into tasks, decision 12): the review cards start with the ticket's project and event and can change them; the server gives the ticket's pair to a card that names none. Cards made from a chat message or a meeting start with none.
- **Tickets:** Project and Event on the ticket page (admins and the group's clients, saved at once through `PUT /api/tickets/:id/project`) and in the new-ticket dialog; the chip on list rows. A žiadateľ sees only the project's name, never its colour or the event (decision 7). A ticket without a client has no project. Moving a ticket to another client clears both.
- **Filters** (decision 19): the group's **Tasks** tab (its first filter row) and **Tickets** tab have a **Project** pill (Any, No project, a project) and, once a project is chosen, an **Event** pill (Any, No event, an event); in the URL (`?project=<id>|none&event=<id>|none`) and remembered per client. A task or ticket edited out of the filter leaves the list live. The global board and the global tickets list show only the Project pill, only while exactly one client is chosen. Server: `400 invalid_filter` for an event without a project and for a project on a cross-client list without exactly one client.
- No notification is sent for a changed project or event (decision 26). Reminders someone sets on an event (F15) are the only event notifications.
- Tests: `modules/tasks/project-links.test.ts`, `modules/tickets/project-links.test.ts` (per role, invalid pairs, inheritance, the move, filters and their 400s, one refs query per page), the EXPLAIN cases in `modules/home/explain.test.ts`, the web tests of the selects, pills and URL params, and `e2e/projects-links.spec.ts` (scenario 2 without the timeline: a task and a ticket on an event, both tabs filtered by it).

## eGrant projects (part P3)

Built (part P3, `feat/projects-intake`). eGrant's side of the API, with examples: [the integration guide](../integrations/egrant-ticket-intake.md#projects). **Before it goes live, the eGrant developers confirm they can send the project call and `project_id` on tickets** (plan, P3).

- **The project endpoint** `PUT /api/egrant/projects/:project_id` (`modules/projects/egrant-routes.ts`) is a webhook eGrant calls whenever it decides, with the full project: name, description and every event (name, `dd.mm.yyyy` date, description; no event ids). Its Bearer key is `EGRANT_PROJECTS_API_KEY`, or the ticket intake's `TICKETS_API_KEY` when that is unset (`egrantWebhookKey`, constant-time compare). Before the body is read, as on every eGrant webhook: `503 intake_disabled` without a key, then its own limit of 120 calls a minute per IP (`429`, wrong keys count too), then `401` for a wrong key. Optionally HMAC-signed (`EGRANT_PROJECTS_SIGNING_SECRET`, ADR 0042; off while unset, and eGrant does not sign today). Body ≤ 1 MiB (`413`). The client is found by the instance's host like a ticket's; a deactivated client answers `409 group_inactive` and nothing is stored (as the intake and the managers webhook), and a stored delivery waits while its client is deactivated.
- **First delivery** (`egrant-delivery.ts`, one transaction under the client's project lock, so concurrent deliveries make one project): the project and its valid events are created **"From eGrant"** (`201 created`) and the client's tickets waiting for that id are linked. If a person's project of the client has the same name key (or alias) and no eGrant id yet, it is linked instead (`200 pending`): its differences become pending changes, nothing is overwritten. A name key already held by a project linked to another eGrant id: the new project is created without the name key row.
- **Skipped events** (an invalid date such as `31.02.2026`, an empty name, or the same name and date twice in one list) are named in `skipped` (`events[2].date`, `events[3].name`, `events[4]`) and logged as `egrant event skipped` with host, project id and field only, never the text.
- **Later deliveries** never change what people see: every differing field becomes a row of **"Changes from eGrant"**: project name and description; per paired event its name, date and description; an unpaired delivered event is an **addition**; an eGrant event missing from the list is a **removal** proposal (never deleted automatically; events people added are never proposed). An equal value deletes the row; a dismissed value stays dismissed until eGrant sends a different one; a changed value replaces the pending one under a new id (an old review of it answers `409 change_outdated`). `200 unchanged` / `200 pending` with the count; the same body again changes nothing.
- **Pairing events without ids** (decision 6b): each eGrant event keeps the identity eGrant last gave it (`egrant_name_key`, `egrant_date`, updated on every delivery), so a person's rename in Help keeps the pairing. In order: same name and date; a unique same name (a redate); a unique same date (a rename); the rest are additions and removals. A rename plus a redate at once, or two events with the same name or date, show as an addition plus a removal; the review shows such pairs as **"Maybe the same event as …"** (each removal next to the pending addition nearest by date).
- **`sent_at`** orders versions: a delivery older than the last processed one of the project's own eGrant id answers `200 stale` and changes nothing. A merged-in eGrant id (a key row only) is not compared: its deliveries only propose changes.
- **Unknown instance**: `202 stored`, the latest version per (host, project id) is kept in `egrant_project_inbox` (an older retry never replaces a newer one). Creating a client or changing its eGrant URL (the groups service, in its transaction) processes the host's stored deliveries as deliveries and deletes them; one that fails stays stored (a savepoint) and never blocks saving the client. The daily job `projects.egrant-inbox-cleanup` (03:35) drops rows older than 180 days.
- **Review** in the project sheet: the section **"Changes from eGrant (n)"** lists one row per field with the current value struck through and the incoming one (descriptions as a before/after pair), the delivery time, and **Accept** / **Dismiss** toggles; rows left alone stay pending; **Save choices** applies them in one transaction (`POST /api/projects/:id/egrant-changes { accept, dismiss }`). An accepted name keeps the old name as an alias (`409 project_name_taken` if another project holds it); an accepted addition creates a "From eGrant" event; an accepted removal deletes the event (its tasks and tickets keep the project without the event) after a confirmation. Admins and the group's clients review (`canEditProjects`; a removal also `canMergeOrDeleteProject`, the same rule); a žiadateľ gets `404`. The project's badge "eGrant changes (n)" in the card and the sheet links to the section, events with a pending change get the mark "eGrant change" in the sheet's list. `?project=<id>` on the Prehľad URL opens that project's sheet.
- **Merge** ("Merge into…" in the sheet's menu, admins and the group's clients, `POST /api/projects/:id/merge { into }`): pick another project of the client (archived ones too); the confirmation names what moves. Events move (their tasks and tickets follow through the event FK), then the other tasks and tickets, files, the attached knowledge (joined up to 10; if one is no longer shareable the survivor keeps only its own), pending and dismissed eGrant changes (the survivor's own row of a field wins) and every name and eGrant id key, so the merged project's name stays an alias and its eGrant id keeps matching the survivor; then the merged project is deleted. Another client's project answers `404`, the project itself `400`.
- **Not built in P3:** the eGrant mark on the timeline's events and in the project select (parts P4 and P2 own those components; they can read the pending rows from `GET /api/projects/:id/egrant-changes`). Linked tickets and a merge send `project:changed` (and `ticket:updated` for tickets linked by a delivery); a merge does not send `ticket:updated` for the tickets it moves, and an inbox processed on a client's save sends nothing (the client was just created or edited).

## Timeline and cards (part P4)

Built (part P4, `feat/projects-timeline`). The Prehľad tab shows, from the top: the **timeline**, the **Tickets** and **Tasks** cards (side by side from 641 px, stacked on phones), then the projects card.

- **Timeline card** (decisions 14–17): the client's events on one straight line, each event a column of the same width (200 px, 160 px on phones), in date order and events of one day by creation. Past events have a filled dot, today's a filled dot with a ring, coming ones a hollow dot; every dot has a ring in its project's colour. Under the dot: the date, the event's name (two lines at most) and, while all projects are shown, the project's name with its dot.
- **Today** is a vertical black rule labelled "Dnes" between the last past and the first coming event (an event of today comes right after it; with no past events it comes first, with no coming ones last). The strip opens scrolled so Today sits about a third from the left; the **Dnes** button scrolls back to it.
- **Gaps:** neighbours more than 60 days apart get a small mark on the line halfway between them ("4 mesiace"; two years and more in years).
- **Which events:** all active projects by default. The **project filter** (2026-10-22, owner request; a pill that opens a checkbox list, a sheet on phones) has "All projects", each active project with a checkbox and an **Only this** button, then the archived ones. Unticking a project while all are shown gives **all except** it (the pill says "All except X"; a project created later shows up by itself); ticking projects after "Only this" gives **only the chosen ones**, their whole life, archived projects too (a later project does not show up until ticked). Ticking an archived project while all are shown turns the choice into a list. The last shown project cannot be unticked. The choice is in the URL (`?project=<id>,<id>` or `?exclude=<id>,<id>`, at most 50 ids, never both), so "Show on the timeline" in the project sheet (`?project=<id>`) and Back work, and remembered per person and client (an overview opened without either gets the last one). With exactly one project chosen, "Add event" goes straight to it and the events carry no project name. 15 events before today and 15 from today load first; **Skoršie** and **Neskoršie** at the strip's ends load 15 more that way and keep what is on screen in place.
- **Under each event** (from 641 px): "Úlohy (n)" with up to 5 open tasks (urgent first, then by deadline), each at most three lines in the narrow column: the title (clipped to two lines, a small red dot before it when urgent, "Urgentné" for screen readers) over a line with the short deadline ("27. okt."; the year only when not this year; red when overdue) and the assignees' avatars, no open circle; the event sheet keeps the full rows, "Tikety (n)" with up to 5 open tickets (newest first, `#number`, subject clipped to three lines, status), each list only when it has rows; "Zobraziť všetko (n)" when there are more, which opens the Tasks tab filtered by the event (`?project=…&event=…`, part P2's filters), or the Tickets tab when only the tickets overflow; then the **done pile**, one muted line "Hotové (7)" that expands in place to the completed tasks (struck through) and resolved tickets, newest first, 20 at a time. A task row opens the task panel over the overview (`?task=<id>`, as on the admin home's board); a ticket row opens the ticket page.
- **Event sheet:** the event's name opens it (on phones the whole top of the column is its tap area): name, date, project, "From eGrant", description, files, attached knowledge, the event's **reminders** (F15, see [reminders.md](reminders.md)), every open task and open ticket (20 a page) and the done pile expanded. `?event=<id>` on the Prehľad tab opens the sheet directly (an event reminder's notification and the dashboard's reminders card link there; without the done pile, which needs the timeline's count). Its menu has Edit (the event dialog) and Delete (asks first; tasks and tickets keep the project). Everyone who reads the group may use them (decision 8a).
- **Header:** the project select, **Dnes**, and **Pridať udalosť**: with one project chosen it opens the event dialog for it, with all projects a menu asks which project first.
- **Empty states:** a client without projects: "Zatiaľ žiadne projekty. Projekty zoraďujú úlohy a tikety tohto klienta na časovej osi." with **Nový projekt**; no events: "Zatiaľ žiadne udalosti." (with **Pridať udalosť** when one project is chosen).
- **Phones** (≤ 640 px): the line, dots, dates, names and projects only; a tap opens the event sheet with the lists.
- **Keyboard:** the strip is a list of events in date order (each a heading with the name as a button, the date as `<time>`); the arrow keys, Home and End move between events and the strip follows the focus. Today is announced as "Dnes, <date>".
- **Tickets card** (decision 18): the client's New and In progress tickets, those I am a riešiteľ of first, then newest first, 8 rows (5 on phones): `#number`, subject, the project (and event) chip, status. The header counts them ("aktívne: 9, moje: 3"); **Otvoriť všetko** opens the Tickets tab (its default: open, anyone).
- **Tasks card:** the client's tasks not in Completed, mine (I am an assignee) first, then urgent, then by deadline (none last), then oldest; 8 rows (5 on phones): title, the project chip, deadline (red when overdue), avatars; the header counts open, mine and urgent ones; **Otvoriť všetko** opens the Tasks tab. Clients see the same cards with their own rows first.
- **Live:** task and ticket events of the group refetch the timeline, the open lists and the cards 2 s after the last one; `project:changed` refetches everything of the tab as before.

## Description editor (part P5)

Built (part P5, `feat/description-editor`). Every long description field is one component, `features/editor/description-field.tsx`:

- **Where:** the task description (task panel and new task; the AI review cards get AI and voice without the picker: a card links its source's shareable items, see `ai-task-split.md`, and more are attached after creating), the ticket text (new-ticket dialog and an admin's edit; with a client only, a ticket without a client keeps a plain textarea), the project and event descriptions, the knowledge item body (note and reminder text, file and link description, meeting notes), the meeting AI summary paragraph, and the finance item description (AI and voice, **no knowledge**: finance stays sealed). Not: titles and names, the meeting transcript, the meeting's decisions and open questions (one item per line lists, kept as plain lists), "Solve with Claude" notes, bulk email blocks, the chat's own edit box.
- **How it looks:** a filled text shows rendered like a chat message with "Edit …"; an empty one opens the editor at once. The editor is the chat's ProseMirror editor in **document mode**: Enter always makes a new line (smart lists as in chat), at least six lines, grows to 16, then scrolls; the chat's eight-button toolbar; at its end the **microphone**, the **AI button** (Fix mistakes, Make it formal, Translate off `.sk`) and **"Attach from the knowledge base"**. Undo of an AI change is one editor undo step (and the AI button's Undo). Value in and out is Markdown, so storage, search and digests did not change.
- **Attached knowledge:** the chat's knowledge picker (unchanged, so it caps one pick at 5; the server takes up to 10) adds items; they show as chips with Remove under the editor and as the chat's cards under the rendered text. Only a client group's public, shareable items can be attached, checked on save (`400 invalid_knowledge_item`: "An attached knowledge item can no longer be shared here. Remove it and save again.") and on every display: an item made admins-only, deleted, or of another client (a ticket moved to another client) shows "Item unavailable" and stays until removed.
- **Mentions (F16, 2026-10-18):** in the task description, the ticket text, the project description and the knowledge item body, `@` opens the chat's people list (the group's clients and its eGrant managers, `isPickable`; no "Everyone in this group": `@all` notifies nobody in a description) and inserts the same pill as in chat (stored `<@id>`). On save, each person **newly** named gets `description.mention` ("Jana mentioned you in the description", opening the task, ticket, project or item; see `notifications.md`); naming someone again in a later edit does not notify them twice, even after removing and re-adding their name, until they have opened the subject: a mention added after they opened it notifies them again (at most once per subject and person between two opens, 2026-10-19), and the author never hears their own mention. An admins-only knowledge item notifies admins only; a ticket only people who can read it. The event description, the meeting AI summary and the finance item description have no `@` list (their saves notify nobody). Since 2026-10-18 an admin also finds these mentions on the dashboard's Mentions card until they open the subject (see `admin-home.md`).
- **Ticket text** is now shown with the chat renderer (line breaks kept; a body with Markdown characters may render as formatting). A žiadateľ opens the items attached to their own ticket's text read-only, with their files.
- **Lazy:** the editor (`description-editor`, 2.5 kB gzip) and the cards (`linked-cards`) are lazy chunks with the `chat` texts; the forms carry only the field shell (`description-field`, 1.6 kB gzip shared, mostly the Markdown renderer the old field had too). The initial JS grew 0.04 kB (the shared schemas).

### AI and voice in the other long-text places (`feat/editor-everywhere`)

Plain-stored text keeps its format and gets the same tools through `features/editor/plain-text-field.tsx` (a textarea with the microphone and the AI button in a lazy chunk with the `chat` texts; no Markdown, no knowledge links):

- **Meeting decisions and open questions** (the summary editor): still one entry per line (`lines` mode: a dictation starts a new line, the AI's list markers and blank lines are cut so the stored `string[]` is unchanged). Group routes.
- **Notes for Claude** ("Solve with Claude", admins) and the **ticket text of a ticket without a client** (admins): admin routes.
- **Bulk email text block** (`bulk-email/rich-text-editor.tsx`): the toolbar gets the same two buttons (lazy `rich-text-ai-tools`). The block is read as Markdown-like text (`rich-text-ai.ts`: `##`/`###`, `- `, `1. `, `**bold**`, `[link](https://…)`) and written back as the builder's own node tree, so the stored format is unchanged. Underline, strike, italic and colours are not sent to the AI; Undo and an appended dictation keep the original tree. Admin routes.

Fields left as they are: one-line names, titles, subjects, codes, emails, URLs and search boxes; the finance work-log note (one line, 500 characters); the meeting transcript (a verbatim record up to 400 000 characters, which the AI limit would cut and a rewrite would falsify); chat composers (already have the tools).

## Finance (part P6)

Built on `feat/finance-projects` (spec §11, decisions 23–25; details in [Finance by project and event](finance.md#finance-by-project-and-event)). A client's Financie tab filters its **Overview** (money and hours) and **Work log** by **Project** and **Event**; a contract may name one of the client's projects, a manual time entry a project and an event; `/finance` filters by project only while exactly one client is chosen. Finance keeps its own copy of each entry's project and event (copied by the time hooks, kept in step on every change of the task's or ticket's project, moved by a merge, kept after a delete), so the projects module never reads finance and finance never reads tasks or tickets.

## History of changes (audit log, 2026-10-19)

The audit log „História zmien“ ([audit-log.md](audit-log.md)) records every project created, renamed or its description changed (only as „zmenený“), archived or restored (`status_changed`), an alias removed, merged (`merged` on the kept project, and the absorbed project's `deleted` as its consequence with `cause_id`) and deleted; and every event created, edited (name, date, description) and deleted. A project and its events made by eGrant's first delivery are recorded with the author **eGrant** (the instance, source `projects`); eGrant's later deliveries only propose, and the person who accepts a change in the review is its author. Deleting a project does not write a row per event. The project's „…“ menu has „História“ for admins.
