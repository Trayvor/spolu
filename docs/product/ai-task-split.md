# Message to tasks with AI

Any chat message can be turned into task cards. An AI reads the message and proposes one card, or several when the message describes several jobs. The user reviews and edits every proposed card, approves or rejects each, and only approved cards are created.

## Requirements

- Every chat message (group chat, task chat and, for admins and the group's clients, ticket chat) has the action **"Turn into tasks"**, next to "Reply in thread". It is shown to everyone who can use the group's board (admins and clients); a ticket's requester, who reads only the ticket chat, never gets it (`POST /api/messages/:id/task-split` answers them `403`).
- A **ticket** (Phase 21, part 21.5) can be turned into tasks the same way from its page: the AI gets the ticket's subject and text, its area and programme as context only, the ticket's chat (the newest 30 messages that are not deleted, thread replies included, oldest first, each cut to 2000 characters, with the author's name), the names of its files (uploaded with it, sent to the intake, or sent in its chat), the group's people and, when the ticket has no project, the client's active projects. The ticket's number and dates are not sent: the AI used to copy them into the cards. A card without a deadline of its own gets the ticket's due date, and a card without a link of its own gets the ticket's URL (its "Link" field). The same review dialog quotes "#123 subject" and the ticket's text; the ticket's uploaded files play the message files' part.
- The message is sent to the AI (OpenAI API) with an instruction to return JSON: a list of one or more tasks, each with a title, a description, a link, a project (or none) and the assignees, deadline and urgency the text gives (see "Project, assignee and link" below). A title is a short action, never with a ticket number or a source; a description says only what has to be done, without labelled metadata lines (number, subject, area, programme, files, dates) and without generic advice (check the logs, reproduce, test) the text does not ask for; it keeps every web address the text gives for the job, copied exactly; it ends with a short "Notes:" paragraph only when the text or the ticket chat gives useful context beyond the job. The link is one web address copied from the text (where the problem is, or what the task is about), or none. The output is in the language of the message, or of the ticket and its chat. A ticket has its own system prompt (`SYSTEM_PROMPTS.ticket` in `ai/openai-provider.ts`), which says later chat messages may correct or settle the ticket. The people list sent with it holds only the group's clients and managers, each marked "eGrant team" (an admin) or "client", and a proposed assignee outside that list is dropped, but a mention in the message text still shows the person's name. The client's active projects go as `id — name` too. The names of the message's files go too (never their contents), and the AI gives each file to the card or cards it belongs to.
- **Nothing of the source is lost** (owner bug report 2026-10-18: a ticket's link did not reach its tasks). Whatever the AI writes, the server makes sure that:
  - a web address of the message's or the ticket's text that no card carries (in its description or as its link) is added on its own line at the end of every card's description; the reviewer removes it where it does not belong. The quote and the ticket chat are context: their addresses are only offered to the AI;
  - a card the AI gave no link takes a ticket's URL, else the one web address of its own description, else, when it is the only card, the one web address of the source text (owner request 2026-10-22; only addresses of the source count, and a text with two or more gives none);
  - a person the text mentions, whom the AI names as "@Name" in a description, is a mention again (a name two mentioned people share stays text);
  - a card made from a ticket links the knowledge items attached to the ticket's text, and a card made from a message those attached to the message, after the card's own, at most 10. Only items still shareable in the group (public, in public folders) go, so a card never shows its readers an item they may not read;
  - a ticket's cards may copy the files sent in its chat as well as its own: everyone who uses the board reads that chat, so a copy shows nobody anything new.
  - Not carried, by design: the ticket's riešitelia (they answer the ticket; a card's assignees come from the text or the reviewer), a message's attached tasks and tickets (the card links back to its message), and a meeting's files and knowledge (the card links back to the meeting; an admins-only meeting's items must not reach the clients). A ticket's project and event are every card's (Phase 33 part P2 decision 12); they win over the AI's project.
- While waiting, the user sees a light "AI is working" animation.
- Then one screen shows every proposed card as the **full task form** (title, description, link, assignee, deadline, urgent, project). The link is the AI's choice, kept only when the source's texts (the message, its quote, the ticket or its chat) have that address, else a ticket's URL, else the one address of the card's description or, for a single card, of the source text, else empty; the reviewer may change it, and the empty-link warning of the create panel does not apply here. The card made by hand (no tasks found) gets a ticket's URL too. The user edits each card separately and **approves** or **rejects** each one.
- Approved cards are created at the top of the **To do** bucket, in the order shown, all at once or none. Nothing is created without approval. A message file kept on a card is copied onto it, so deleting the task never removes the message's file.
- The source message is then marked **"Turned into tasks"** with links to the created tasks.
- Limit: no limit (owner, 2026-10-15). Every call is logged with its token usage so the cost can be watched.
- Example of done: a message with 5 jobs becomes 5 cards after the user's review, and the message links to them.

## Phase

Phase 9. Status: built (local).

- Server: AI client and `POST /api/messages/:id/task-split`; creating the approved cards with `POST /api/groups/:id/tasks/from-message`, at the top of To do, all or nothing, message files copied. A message of a ticket chat also sets the cards' ticket. Tickets (part 21.5): `POST /api/tickets/:id/task-split` (404 unreadable, 409 `no_client`, 403 for a requester, then the same answers as for a message) and `POST /api/groups/:id/tasks/from-ticket` (`{ ticketId, tasks }`, the ticket's uploaded files and its chat's files as `messageFileIds`; the split lists them in its answer's `files`, since the ticket page has only the uploads); both creates go through `createTasksFromSource` in the tasks service, announce `ticket:updated` and record `ticket.tasks` with the count for the people who hear the ticket's updates.
- The "Generate tasks from text" button on the boards carries the sparkle icon (`SparkleIcon` in `components/icons.tsx`, shared with the composer's AI button). Review screen (as built, `apps/web/src/features/task-split/`): "Turn into tasks" sits in the message's "More" menu on desktop and in the phone action sheet, only while `GET /api/ai/status` says `taskSplit: true` and only on messages with text. It opens a dialog (a centred 720 px dialog on a computer, a full-screen sheet on a phone) that quotes the message and shows "AI is reading the message…" with three card outlines. The proposed cards then all show at once as compact summaries (title, two lines of description, assignees, deadline, urgent, the card's project as the board's project chip, the message files proposed for that card). A card is edited only after it is opened: on a computer it opens in place as the full task form (one at a time; opening another closes the first and keeps its edits), on a phone as a full-screen layer with "Done". Each summary has "Approve" and "Reject" (44 px), and the footer "Approve all". Approving a card that is not valid (an empty title) opens it with the error instead. A rejected card shrinks to one struck-through line with "Undo". "Create N tasks" works only when every card is approved or rejected and at least one is approved; it sends one request (a double click never sends twice). Message files on a card can be removed and new files uploaded; the message's files go as `messageFileIds` (copied), the uploads as `fileIds`. If creating fails with `invalid_assignee` (someone chosen stopped being a client or manager), the dialog shows "Someone you chose can't be assigned here any more.", keeps the cards and refetches the group's people. On success the dialog closes and a toast says "N tasks created" with "Open the board". The dialog takes a `source` (`{ kind: 'message', message }` or `{ kind: 'ticket', ticket }`, `review-model.ts` `SplitSource`) and loads with the `forms`, `tasks` and `taskSplit` namespaces; the ticket page opens it from `features/tickets/ticket-tasks.tsx`, the ticket chat through `useMessageTaskTools`.
- Errors stay in the dialog: the AI did not answer (502, "Try again"), found no tasks (422, "Create one task by hand": one card with an empty title and the message text as description, opened for editing), AI not available (503), message deleted (404). A failed create keeps every card and says why (message deleted, a file no longer available, or try again).
- Closing: the backdrop does nothing; Escape or Cancel close at once when nothing was decided or edited, else ask "Discard the proposed tasks?".

## Project, assignee and link (owner request 2026-10-22)

The AI split of a message, a pasted text or a ticket also fills a card's project and is told more precisely how to find the assignees and the link. Files are not part of this (no upload).

- **Project.** The AI gets the client's active projects (`id — name`, at most 100, by name; archived ones never go) and sets `projectId` only when the text clearly refers to one project: by its name, a close variant (an abbreviation, another word order or case, missing diacritics) or unmistakable context; otherwise null, and never only because a single project exists. The server keeps it only when it was offered (`sanitizeProposals`). A ticket that has a project sends no project list: its project (and event) is every card's and wins over the AI. In the review the proposed project is preselected in the card's Project select and shown on the compact card as the project chip (name and colour from the select's own list, `GET /api/groups/:id/projects/picker`, loaded only when a card has a project other than the ticket's); the reviewer can change or clear it. A card with the AI's project starts without an event.
- **Assignee.** The prompt asks for the people the text gives the job to: named by full name, first name, surname, a short or familiar form ("Zuzka" for Zuzana) or an @mention. Each person is marked eGrant team or client, so "eGrant should…" or "the client will send…" assigns the one person on that side when there is exactly one. A name that fits several people, or a text that points at nobody, leaves the card unassigned: the AI never guesses. Only the pickable people are kept.
- **Link.** Besides the AI's own choice, the server fills an empty link (see "Nothing of the source is lost" above); a web address of the text still stays in a description as before.
- **Privacy.** Project names now leave the server with the rest of the prompt (to OpenAI); project descriptions, events and files do not.

## Meetings (Phase 30)

A meeting's action items open the same review dialog (`source` `{ kind: 'meeting', item }`). The proposals come from the stored summary without another AI call (`POST /api/knowledge/:id/meeting/task-proposals`: the text as the title, the meeting's title and date in the description, a uniquely matched person of the group as the assignee, the said date as the deadline). The dialog adds a bucket select ("Add to", the group's buckets except Completed, To do by default); `POST /api/knowledge/:id/meeting/tasks` (`{ bucketId?, tasks }`, admins, up to 30 cards) creates them at the top of that bucket through `createTasksFromSource`.

## From a pasted text (owner request 2026-10-21)

The top of both task boards (a client's board, and the admins' global board "Úlohy") has the button "Vygenerovať úlohy z textu", shown only while the AI is on. It opens a dialog: type or paste a text (up to 10,000 characters), then the same review as for a message (`ReviewDialog`, source `text`: title, description, assignees, due date, urgent, link, files uploaded in the review, and the column to add to, To do by default). On the global board the person picks the client first; it is preselected when the board is filtered to exactly one client.

- `POST /api/groups/:id/task-split-text` `{ text }` returns the proposals (same errors as the message split: 422 `ai_no_tasks`, 502 `ai_failed`, 503 `ai_unavailable`). Whoever reads the group may call it (admins, the group's clients); anyone else, and a missing group, get 404.
- `POST /api/groups/:id/tasks/from-text` `{ bucketId?, tasks }` creates the approved cards (same rules and permission as the other `from-*` routes). The cards have no source link; the text is not stored.
- MCP (2026-10-21): `suggest_ticket_task_split` and `suggest_message_task_split` return the proposals (they create nothing; each card's `projectId` too since 2026-10-22), `create_task_from_ticket` and `create_task_from_message` create the reviewed cards through the `from-*` routes; there is no "from text" tool (an MCP client creates cards from a text with `create_task`). See [mcp.md](../integrations/mcp.md).
- Voice input is not in this dialog (the chat composer's recorder is not shared); type or paste.
