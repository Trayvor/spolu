# 0050 Passkeys for admins with SimpleWebAuthn, next to the email code

Date: 2026-10-18
Status: accepted

## Context
The owner asked for passkeys (WebAuthn) for admins as an alternative to the email-code login, which stays and stays the default. Clients and žiadatelia keep the code login only. WebAuthn needs CBOR, COSE keys, attestation formats and signature checks on the server and the credential API's binary conversions in the browser; writing that ourselves is the riskiest kind of code to own. better-auth 1.7 has a passkey plugin, but it registers passkeys for any user, keeps its own challenge cookie and table shape, and has no hook for "admins only, a fresh session or an emailed code first, and a notice email".

## Decision
- **Libraries:** `@simplewebauthn/server` 14.0.3 (server) and `@simplewebauthn/browser` 14.0.0 (web), pinned exactly, both older than two weeks (supply-chain policy, [ADR 0037](0037-supply-chain-policy.md)). MIT, maintained, used by most Node passkey stacks. No better-auth passkey plugin.
- **Our own code around them** (`apps/server/src/modules/auth/passkeys.ts`, `passkey-routes.ts`, `passkey-login.ts`): one table `passkeys` (migration 0059), challenges in better-auth's `verification` table (`passkey-register:<userId>`, `passkey-login:<challenge>`), five minutes, deleted by the first answer (single use). The RP ID is `PUBLIC_URL`'s host and the only accepted origin `PUBLIC_URL`'s origin (plus Vite's `http://localhost:5173` in development). Discoverable credentials (`residentKey: required`), `userVerification: required` checked again on the answer, attestation `none`, the signature counter must grow when the authenticator counts (the update is a compare-and-set, so two answers against one counter cannot both win), and the answer's user handle must be the stored one. The user handle is an HMAC of the user id with `APP_SECRET`, never the id.
- **Registration** (`/api/me/passkeys*`): a real cookie session of an admin (no in-process MCP call). A session younger than 10 minutes registers directly; an older one first confirms a 6-digit code emailed to the admin (5 minutes, 3 tries, as the login code). At most 10 passkeys per admin; the admin gets a notice email for each one added, as for a new MCP token.
- **Login** (`POST /api/auth/passkey/options`, `POST /api/auth/passkey/sign-in`): better-auth plugin endpoints, so the session, its cookie, the session hooks (a disabled account cannot sign in) and better-auth's Origin check are those of the code login. A passkey whose user is no longer an admin or is deactivated answers `PASSKEY_INVALID`, and the login page points to the email code; deactivation deletes the passkeys. Rate limits per address: the sign-in at `LOGIN_CODES_PER_MINUTE`, the options at six times that (the login page asks for them once per visit of the email step, and only where the browser supports autofill). These counters are their own: better-auth counts the email code per address and path, so passkey calls never use up an address's code budget.
- **Browser:** the login page offers "Prihlásiť sa kľúčom (passkey)" under the email form and, where the browser supports it, conditional mediation on the email field (`autocomplete="username webauthn"`). `@simplewebauthn/browser` is imported only with `import()`, so it is its own lazy chunk (3.7 kB gzip) and never in the initial JS.
- **CSP:** unchanged. WebAuthn is a browser API, not a fetched source; the library has no inline script and no `eval`.

## Consequences
- Passkeys are bound to the domain of `PUBLIC_URL`. Moving Help to another domain (see [deploy.md](../runbooks/deploy.md#moving-to-a-new-domain)) makes them useless there; admins log in with the code and add new ones.
- A library update is a dependency bump under the supply-chain policy; the server tests check real ES256 attestations and assertions made by a software authenticator (`apps/server/test/webauthn.ts`), the e2e test uses Chromium's virtual authenticator, so a breaking change shows up in CI.
- Attestation is not checked (`none`): any authenticator the admin's browser offers is accepted. Enough for an alternative to an email code; an allow-list of authenticator models would need attestation and the FIDO metadata service.
