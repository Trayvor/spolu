# 0075 Tickets are assigned to the client's managers and finished by both sides

Date: 2026-11-04
Status: accepted (supersedes [0064](0064-ticket-area-autoassign-table-replaced-by-egrant.md) and [0069](0069-ticket-area-rules-by-clients-and-sources.md), amends [0021](0021-ticket-riesitelia-and-watching.md))

## Context
Tickets now mostly carry questions from clients' managers, answered by admins, yet the system still assumed a wide audience: a per-client table of automatic assignees by area (ADR 0064, ADR 0069), a personal "Watch tickets" switch (ADR 0021) and a free-text grant programme. A ticket could reach nobody, and it stayed In progress for as long as its author kept quiet. The owner asked (2026-11-04) that nobody configures assignment, that a ticket belongs to a project, and that both sides say when it is finished. Full design: [spec](../superpowers/specs/2026-11-04-ticket-lifecycle-rework-design.md).

## Decision
- **Assignment is derived, never configured.** A client's admin managers (`group_managers`, active, a substitute's derived rows included) become riešitelia of every new ticket, on top of anyone assigned; a ticket that gets or changes its client takes them only when it has no riešiteľ left; a new manager takes only the client's open tickets without one. The handler is registered with the groups module and runs in the same transaction (`manager-assign.ts`, `onManagerGained`). The limit of 10 holds. Migration 0077 applies the rule once to every open ticket, with audit rows and no notifications.
- **`ticket_area_rules` and `ticket_watch_settings` are dropped** (migrations 0076, 0077), with `PUT /api/egrant/ticket-areas`, `GET`/`PUT /api/groups/:id/ticket-areas`, `GET`/`PUT /api/groups/:id/ticket-watch` and the MCP tools `list_ticket_areas`, `set_ticket_areas`, `get_ticket_watch`, `set_ticket_watch`. Old audit rows stay readable, so their labels stay. `area` stays as a field and a list filter.
- **The audience is one rule.** A ticket's riešitelia, or every active admin while it has none, and its initiator. Other clients of the group stop hearing about colleagues' tickets. A just-assigned manager gets only `ticket.assigned`. A 👎 reaches the admin riešitelia, or every active admin who reads the ticket when it has none, so the alert is never lost. The dashboard lists a viewer's tickets and every open ticket without a riešiteľ, through a new partial index `tickets_open_created_idx`.
- **No new status.** Finishing is a mark on an `in_progress` ticket: `admin_done_at` and `admin_done_by`, cleared in the statement of any status change or client move, so every `('new', 'in_progress')` query and the Open filter stay. Lists derive the badge. `admin_done_cleared_at` records that a mark ended without being set again (by the author, a status change or a move), or that the ticket left `resolved`, and drives the time review.
- **The author answers, or silence ends it.** Only the people who can rate a ticket can confirm it (`canConfirmTicket` is `canRateTicket`); a ticket with nobody to ask resolves at the press. A declined mark or any message of the author clears it. `tickets.auto-resolve` resolves a mark 5 calendar days old (`TICKET_CONFIRM_DAYS`): hourly at :15, one transaction per ticket with `for update skip locked` and a re-check of the locked row, keyset paging on `(admin_done_at, id)` over a partial index. It throws until the app has attached its deps and sockets, because the job is built first and must announce after each commit.
- **Time moves to the press.** The dialog asks when the admin finishes, not at `resolved`; one entry per admin per ticket stays. Entries filled while the ticket is marked count on the press's day. A ticket that came back asks those with filled time to review it: `finance_time_entries.review_requested_at` (migration 0080) marks it, and missing-time reports read `minutes` only, so a review never counts as missing. An admin resolving directly with the mark set is asked as usual, and nobody else is told.
- **Opening starts the work** through the page's `POST .../seen`, never a `GET`, so MCP reads never count. The update is conditional on `status = 'new'`.
- **The project replaces the programme** in the app, the API and MCP. The intake's `programme`, the column, the name match of `TICKETS_PROJECT_FIELD=programme` and the AI context stay, so eGrant's requests keep working.
- **The email queue drains faster** (four at once, polled every second): with every admin hearing tickets without a riešiteľ, bursts of digests held login codes behind the 30 s backstop poll.

## Consequences
Nobody configures assignment and a new ticket of a client with a manager always has someone answering it. A ticket never stays In progress only because its author went quiet. The area table with its dialog and the watch switch with its settings column go. A client without a manager, or a ticket without a client, reaches every active admin, which is noisier than before for those tickets; a ticket whose only riešiteľ was deactivated reaches nobody and sits on no dashboard until someone is assigned. A message of thanks clears the mark: Help does not guess what a message means, and the admin presses the button again. eGrant's `ticket-areas` call must go before the release: it answers `404` afterwards.
