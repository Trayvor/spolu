# 0070 Bulk email tracking through Elastic's signed webhook

Date: 2026-10-22
Status: accepted (builds on [0016](0016-bulk-email-through-elastic-v4-emails.md))

## Context
The bulk email report showed only Spolu's own send results; "opens and clicks are not measured" (Phase 23, spec "Later", item "Webhook tracking"). The owner approved building the webhook (2026-10-22). Elastic Email reports events through webhooks ("notifications", PRO plans): `Sent`, `Opened`, `Clicked`, `Error` (bounces), `AbuseReport` (complaints) and `Unsubscribed`; there is no separate "Delivered" event. Every bulk email already carries `Content.Postback = <campaignId>:<userId>`, which Elastic echoes as `postback`.

What Elastic documents, checked 2026-10-22:
- **Signing** ([elasticemail-examples, docs/webhooks.md, "Verifying a signed request"](https://github.com/ElasticEmail/elasticemail-examples/blob/main/docs/webhooks.md)): a webhook created with `EnableSigning: true` and `DeliveryMethod: PostJson` (both chosen at creation only, [v4 OpenAPI](https://api.elasticemail.com/public/v4/swagger) `WebhookCreatePayload`) sends `X-ElasticEmail-Timestamp` (unix seconds), `X-ElasticEmail-Signature` (`v1=<lowercase hex>`, a comma-separated list; any `v1=` entry may match) and `X-ElasticEmail-Webhook-Id`. The hex is `HMAC-SHA256(secret, "{timestamp}\n{METHOD}\n{request target}\n{raw body}")`, the request target being the path and query exactly as received. Reject timestamps more than 5 minutes off; compare in constant time; answer 401 on a mismatch (Elastic retries for up to 24 hours). Signed webhooks do not follow redirects. The doc's two test vectors are in our unit tests and pass.
- **Payload** (same doc, "What arrives", and the help article [Notification settings](https://help.elasticemail.com/en/articles/4804685-notification-settings)): a flat JSON object with lowercase names `status`, `to`, `from`, `subject`, `date` ("date and time of the event, UTC"; the only example is `3/10/2012 10:20:30 AM`), `transaction`, `messageid`, `category` (bounce category), `target`, `channel`, `account`, `postback`, `ip`, `useragent`, `country`, `state`, `city`.
- **Test event**: saving a webhook (or changing its URL) sends a test event with sample values and `status=opened` in lower case. For a new signed webhook a 401/403 answer is accepted (the endpoint cannot know the new secret yet); after a URL change only a 2xx is.
- **Bounce categories** ([What are the bounce error categories](https://help.elasticemail.com/en/articles/2300650-what-are-the-bounce-error-categories-and-filters)): only `NoMailbox` is documented as permanent ("will permanently turn the contact's status to Invalid"); the rest are temporary or not classified.

## Decision
- **Config.** `ELASTIC_WEBHOOK_SECRET` (optional, ≥ 16 characters) on the `elastic` bulk driver (`config.bulkEmail.webhookSecret`); with the `smtp` driver it is a `ConfigError`. Unset: `POST /api/bulk-email/webhook` is not registered (404) and the sender keeps `TrackOpens`/`TrackClicks` false. Set: both are true, so nothing is tracked that nobody receives.
- **Route.** `POST /api/bulk-email/webhook`, public, its own plugin with a catch-all string body parser (64 kB) so the signature is checked over the raw bytes before parsing; `request.url` is the request target. Missing, forged or stale (±300 s) signatures are 401. 1200 calls a minute per address (Elastic bursts; refused calls are retried). Exempt from the CSRF guard (the signature is the credential). No replay cache: events are idempotent.
- **Events.** `Sent` → `delivered`, `Opened` → `opened`, `Clicked` → `clicked`, `Error` → `bounced`, `AbuseReport` → `complaint`, `Unsubscribed` → `unsubscribed`; any other status (the lower-case test event) and any postback that is not `<campaignId>:<userId>` of an existing recipient row (test sends use `test:…`) are answered 200 and ignored, logged at info without the body.
- **Storage.** `bulk_events` (migration 0073): primary key `provider_event_key` = SHA-256 of `[messageid, transaction, postback, status, date]`, so retries and repeats are stored once; `campaign_id`, `user_id` (FK to the recipient row, cascade), `kind`, `occurred_at` (Elastic's date read as UTC; unreadable or in the future: the time received), `category`. No address, IP, user agent or URL. The recipient row keeps the first time per kind (`delivered_at`, `opened_at`, `clicked_at`, `bounced_at`, `complained_at`, set with `least()`), so the report counts each person once with one scan of the campaign's recipients and the per-person list gets flags for free.
- **Suppression.** A complaint, an `Unsubscribed` event or a `NoMailbox` bounce calls `suppressPeople` (split out of the daily sync's `applyProviderSuppressions`): source `provider`, `changed_at` = the event's date, never over a newer change in Spolu. Only bulk email reads it.
- **Report.** `BulkCampaignDto.tracking = { delivered, opened, clicked, bounced, complaints }` (the detail query only; the list is unchanged), `BulkRecipientItem.opened/clicked/bounced`. The web shows a second card once any count is non-zero, with the note that opens are approximate. No socket event per webhook call (bursts); the report refetches as before.

## Consequences
- The owner creates the webhook in Elastic (PRO plan) with POST (JSON body), signing on and the final URL `https://help.egrant.sk/api/bulk-email/webhook` (not the old `spolu.egrant.sk`, which redirects), and copies the secret shown once into `ELASTIC_WEBHOOK_SECRET`; see the [deploy runbook](../runbooks/deploy.md#bulk-email-pre-launch-checklist). The first test event at creation gets 401 (no secret yet), which Elastic accepts.
- Click tracking rewrites links through Elastic's tracking domain (the `tracking` CNAME of the sender domain, if set); in `spolu` unsubscribe mode the footer link is rewritten too, the `List-Unsubscribe` header is not.
- Opens are approximate (Apple Mail Privacy Protection opens every message; many apps block images).
- Events of campaigns sent before tracking was on still count `Sent`, bounces and complaints, but not opens or clicks.
- Rotating the secret in Elastic needs `ELASTIC_WEBHOOK_SECRET` updated at once; events rejected meanwhile are retried for 24 h.
